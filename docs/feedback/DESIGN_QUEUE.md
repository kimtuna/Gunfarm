# DESIGN_QUEUE — 그림·모션 루프의 큐

> 이 큐는 **`docs/DESIGN_LOOP.md` 의 루프**가 돈다. `docs/feedback/INBOX.md` 와 섞지 않는다.
>
> **이 큐의 산출물은 `docs/MOTION.md` 다.** 그림은 결과물이고 문서가 원본이다 —
> 왜 그 동작이고 왜 그 값인지가 안 남으면 다음 바퀴가 되돌린다
> (`DESIGN_LOOP.md` 「이 루프의 산출물은 문서다」).
>
> **끝나는 조건은 하나다 — 사람이 직접 보고 「누가 봐도 퀄리티가 떨어지지 않는다」**
> (`DESIGN_LOOP.md` 「끝나는 조건은 하나다」). **QA 통과는 「닫아도 된다」가 아니라
> 「사람에게 보여도 된다」는 뜻이다.**
>
> **상태 셋:** `- [ ]` 미완료 · `- [~]` **사람 확인 대기** · `- [x]` 완료.
> **화면에 보이는 것이 바뀌면 루프는 `- [~]` 까지만 하고 다음 항목으로 간다.**
> 화면이 안 바뀌는 것(QA 검사 추가·코드 정리)만 루프가 `- [x]` 로 닫는다.
>
> **항목 갈래:** `[바탕]` 이게 안 되면 아무 모션도 평가할 수 없다 · `[자]` 자가
> 재는 것이 있다 · `[취향]` 사람 눈으로만 갈린다. **셋 다 화면이 바뀌면 사람이 닫는다** —
> 갈래는 「무엇으로 판정하나」이지 「누가 닫나」가 아니다.
>
> 번호는 `#d1` 부터.

## 이번 판은 **재설정**이다 (2026-09-10 사람 결정)

*"아깐 우리가 찾은 비율 있잖아? 그걸로 다시 게임 세팅 다시 만들고 싶어.
그에 따라 모든 디자인 다 없애고 전부 다시 만들게."*

**손보는 게 아니라 새 규격 위에서 다시 만든다.** 목표 규격은 이것이고, 근거는
`docs/DESIGN.md` 「카메라 / 해상도」와 「아이템/오브젝트 크기 표준」에 숫자까지 있다:

| | 지금 | **목표** |
|---|---|---|
| 논리 해상도 | 1440×810 | **1920×1080** (1080p 1배 · 4K 2배 — 지금은 어디에도 정수배가 아니다) |
| 보이는 칸 | 30 × 16.9 | **40 × 22.5** |
| 타일 아트 | 48px | **48px (안 바뀐다)** |
| 시트 칸 | 96px | **96px (안 바뀐다)** |
| **인물 키** | 96px (2.00칸) | **72px (1.50칸)** |
| **등신** | 3.7 | **2.8** (`heads` 3.6 → 2.77) |
| 머리 | 26px | **26px — 얼굴 픽셀은 한 개도 안 줄인다** |
| 캐릭터 화면비 | 11.9% | **6.7%** |

### 지워도 되는 것 / 지우면 안 되는 것

| | |
|---|---|

전부 `git` 이 들고 있으므로 **지운 것은 언제든 되돌아온다.**

### 순서를 지켜라

**뼈대가 고장난 채로 다시 구우면 고장난 것을 다시 굽는다.** 2026-09-10 에 옆모습 팔이
아예 배정 안 돼 있는 것을 모르고 여러 바퀴를 돌았다.

```
A 판 깔기(#d1)  →  B 배경(#d2~#d4)  →  C 오브젝트(#d5~#d8)
   →  D 캐릭터 바탕/버그(#d10~#d15)  →  E 캐릭터 그림(#d20~#d21)
   →  F 모션(#d30~#d39)  →  G 도구·아이템(#d40~#d42)  →  H 한 화면(#d50)
```

**A 가 끝나면 화면이 보인다.** 그전에는 그림이 하나도 없어서 게임이 안 돈다.

## 다루는 범위 — **화면에 보이는 것 전부**

사람 지시(2026-09-10): *"디자인 전체적으로 다시 만들어줘. **배경부터** 나무 돌 이런
것들도 다 다시 만들어야 되는데."*

| 갈래 | 무엇 | 지금 |
|---|---|---|
| **땅과 바다** | 풀 · 깊은 바다 · 얕은 바다 · 물거품 · 해안선 | 다 지웠다 |
| **월드 오브젝트** | 나무(가로 2칸 × 세로 3칸) · 바위(1칸) · 덤불(1칸), 각 3변주 | 다 지웠다 |
| **캐릭터** | 22시트 (idle · 걷기 · 도구 7종 × 3모션) × 4방향 | 다 지웠다 |
| **도구** | 아이콘 7 · 바닥 그림 7 | 다 지웠다 |

**순서는 「보이는 것」 기준이다.** 배경 → 오브젝트 → 캐릭터 → 도구. 캐릭터의 뼈대
버그들은 **캐릭터 그림의 전제조건**이라 그 앞에 두지, 큐 맨 앞에 두지 않는다 —
그걸 먼저 하면 사람이 한참을 기다려야 화면이 바뀐다.

# A단계 — 판을 깐다 (게임이 다시 돌게)

지금 **그림이 하나도 없어서 게임이 안 돈다.** 먼저 새 규격으로 전부 구워 놓고,
그 위에서 하나씩 다시 그린다. **A단계가 끝나면 화면이 보인다.**

- [ ] #d1 [바탕] **새 규격을 코드에 넣고 전부 다시 구워 게임이 돌게 만든다.**
  읽을 것: `docs/DESIGN.md` 「카메라 / 해상도」·「크기 표준」 · `docs/CHARACTER.md`

  **이 항목만은 `project.godot` 을 건드려도 된다** (`PROMPT_DESIGN.md` 의 「엔진 코드는
  건드리지 않는다」에 대한 유일한 예외다 — 논리 해상도는 엔진 설정이면서 동시에
  그림 규격이라, 갈라두면 두 루프가 서로를 기다린다). `INBOX #75` 는 이 항목이
  흡수했다 — 그쪽은 닫아라.

  ```
  game/project.godot   viewport 1440×810 → 1920×1080 · window_override 1280×720 → 1920×1080
  game/tools/comfy.py  FIG_HEADS 3.6 → 2.77
  game/tools/rig.py    인물 키 96 → 72        # joints() 의 h
  ```

  **`heads` 를 같이 내리는 것이 핵심이다.** `joints()` 는 **머리만 `H = h/heads` 로
  재고 상체·하체·팔은 `h` 로 잰다.** `h` 만 줄이면 얼굴까지 죽는다. `heads` 2.77 이면
  `H = 72/2.77 = 26px` 로 **머리 26px · 눈 3px 이 그대로 남는다.**
  어깨·엉덩이 폭과 팔다리 굵기는 전부 `h` 의 비율이라 **손대지 마라** — 저절로 따라온다
  (사람 결정: *"당연히 몸도 같이 얇아져야지"*). 가장 가는 정면 허벅지가 6 → 4.5px 로
  사라지는 부위가 없음을 실측했다.

  **시트 칸(`cell`)은 96px 그대로** 둔다. 인물이 72px 이 되어 24px 이 남고, 그 여유가
  가로로 넓은 도구를 받는다 — `INBOX #72` 가 이걸로 풀린다(끝나면 22장의 `th` 를 재서
  한 값이면 그쪽도 닫아라).

  **그 다음 `game/tools/` 의 생성기를 전부 돌려 41장을 다시 굽는다.** 지형·오브젝트·
  아이콘·상자·자리표시까지. 디자인은 **아직 옛것 그대로** — 이 항목은 **크기와 규격만**
  맞추는 것이고, 그림을 예쁘게 만드는 것은 B단계부터다.

  `--headless --path game --import` 로 **반드시 재임포트**하고 `.import` 도 같은 커밋에
  넣어라(`CLAUDE.md`).

  **눈으로 볼 것**: 월드 캡처 한 장. 캐릭터가 화면 세로의 **6.7%**, 보이는 칸이
  **40 × 22.5** 여야 한다.
  자체 QA: `qa_character_sheets.py` `qa_sprite_check.py` `qa_player_sprite` `qa_player_walk`
  `qa_player_world` `qa_character_sprite` `qa_ground_items` `qa_terrain_view` `qa_uid_files`.

  **미리 아는 위험**: 걷기 모션 값(`STRIDE`, 허벅지·무릎 각도)이 96px 다리에 맞춰져
  있다. 다리가 36 → 27px 이 되므로 **짧은 다리가 과장되게 휘적거릴 것**이다. 그건
  D단계에서 잡는다 — 여기서는 QA 만 통과시키고 넘어가라.

# B단계 — 배경 (땅과 바다)

**사람이 「배경부터」라고 했다.** 화면의 대부분을 차지하고, 캐릭터·오브젝트의 크기를
재는 기준이 되는 것이 배경이다.

- [ ] #d2 [취향] **초원이 벽지처럼 보인다 — 칸마다 풀 양이 달라야 한다.**
  (2026-09-10 사람 지적: *"초원 표현도 드문드문 풀이 있어야지 하나만 만드니까 너무
  별로야"*.)
  읽을 것: `docs/WORLD.md` 「지형 무늬」 · `docs/STYLE_GUIDE.md` 6번

  `INBOX #62` 가 잡티를 덩어리로 만든 것까지는 옳았다. 틀린 것은 **그 덩어리를 칸마다
  똑같이 하나씩** 놓은 것이다 — 무늬 변주가 8종인데 **덤불 수가 다 같아서** 모든 칸이
  같은 그림이고, 화면이 되풀이 무늬로 보인다.

  **고칠 것**: `gen_terrain.py` 의 `GRASS_TUFTS` 는 **넓이당 개수**라 칸마다 같은 양이
  나온다. 무늬 변주(8종)마다 **덤불 수를 0~3 개로 벌린다.** 맨땅이 드러난 칸이 섞여야
  「드문드문」이 읽힌다.

  **줄이지 말 것**: 덩어리 하나의 **크기**(잎 8~14px · 굵기 2~3px). 줄이면 잡티로
  되돌아간다 — `INBOX #62` 가 값을 치르고 올린 값이다.

  **바다는 건드리지 않는다** — 물결은 고르게 뿌려야 한다(몰면 타일 모서리에 가로줄이
  비친다. 「이음매」 실측 1.31, 상한 1.10).

  **눈으로 볼 것**: 월드 캡처. 풀이 성긴 데와 우거진 데가 있어야 하고, **되풀이가
  눈에 안 잡혀야** 한다.
  자체 QA: `qa_sprite_check.py` 의 「변주」·「무늬」·「이음매」가 그대로 통과해야 한다.
  **「변주」에 덤불 수의 폭을 재는 항목을 더한다** — 8종이 서로 다르기만 하면 통과하던
  검사라 이번 문제를 못 잡았다.

- [ ] #d3 [취향] **바다 — 물결이 「긁힌 자국」이 아니라 물로 보여야 한다.**
  읽을 것: `docs/WORLD.md` 「지형 무늬」 · `docs/STYLE_GUIDE.md` 6번

  `INBOX #62` 가 물결을 **「골 + 마루」 한 쌍**으로 바꿔 놓았다(그전에는 1px 짜리 가로
  획이 흩뿌려져 긁힌 자국이었다). 그 뒤로 사람이 눈으로 본 적이 없다 — **A단계 캡처를
  보고 판단하는 것이 이 항목의 시작이다.**

  **되돌리지 말 것**: 바다는 **고르게 뿌린다.** 풀처럼 한자리로 모으면 칸 안에 넓은
  맨물이 남고 그 자리가 타일 모서리에 걸려 **가로줄이 비친다**(「이음매」 실측 1.31,
  상한 1.10. 고르게 뿌리면 0.61). 그리고 **깊은 바다 램프만 폭이 1.80** 이다 — 기본
  명도가 56 이라 좁은 램프로는 남색 한 판이 된다.

  자체 QA: `qa_sprite_check.py` 의 「이음매」·「무늬」·「변주」·「채도」·「평균명도」.

- [ ] #d4 [취향] **해안선 — 섬의 테두리가 화면에서 제일 큰 지형지물이다.**
  읽을 것: `docs/WORLD.md` 「지형 무늬」

  `INBOX` 에 *"해안선 자체가 화면에서 제일 큰 지형지물이 된다"* 는 기록이 있다.
  **A단계 캡처에서 해안선이 계단으로 보이는지, 테가 둘러진 것으로 보이는지**부터 본다.

# D단계 — 캐릭터 바탕 (버그. 이게 안 되면 캐릭터 그림을 평가할 수 없다)

**2026-09-10 에 옆모습 팔이 아예 배정 안 돼 있는 걸 모르고 「팔이 V자로 굳었다」를
여러 바퀴 논의했다.** 그림을 고치기 전에 배관부터 고친다.

- [ ] #d10 [바탕] **AI 에게 준 뼈대와 그림을 자르는 뼈대가 서로 다르다 (옆모습).**
  읽을 것: `docs/CHARACTER.md`

  **뼈대는 그림에서 뽑는 것이 아니라 숫자에서 계산된다.** 그리고 같은 숫자로 두 가지를
  만든다 — ① `comfy.figure()` 가 ControlNet 용 뼈대 그림을 그려 **AI 에게 이 자세로
  그리라고 시키고**, ② `rig.joints()` 가 같은 좌표로 **그 그림을 부품으로 자른다.**
  같은 숫자에서 나오니 맞아야 하는데, **두 함수가 옆모습에서 다르다:**

  | | `comfy.figure()` (AI 에게 준 것) | `rig.joints()` (자를 때 쓴 것) |
  |---|---|---|
  | 정면 어깨 반폭 | `h*0.105` = 44.1px | `h*0.105` = 44.1px — 같다 |
  | **옆모습 어깨 반폭** | **`H*0.12` = 14.0px** | **`h*0.105` = 44.1px** — **30.1px 다르다** |
  | **옆모습 골반 반폭** | **`H*0.10` = 11.7px** | **`h*0.070` = 29.4px** — **17.7px 다르다** |
  | **옆모습 팔을 몸 앞으로** | `fr = h*0.035` = 14.7px · `fl = h*0.015` = 6.3px | **아예 없다** |

  `comfy.figure()` 는 옆모습에서 어깨·골반을 **일부러 접는다.** 주석에 이유가 있다 —
  *"폭이 같으면 프롬프트에 side view 를 넣어도 정면을 그린다(실측)."* 그리고 옆모습은
  **두 팔이 같은 쪽(앞)으로** 가야 해서 `fr`/`fl` 로 앞으로 민다.
  **`rig.joints()` 는 이 셋을 하나도 안 한다.**

  그래서 AI 는 접힌 어깨로 옆모습을 그렸는데, 자를 때는 안 접힌 뼈대를 대고 잘랐다.

  **실측 (칸 중심 cx=768 기준 오른 어깨 x):**

  | | x |
  |---|---|
  | AI 가 받은 뼈대 | 782.0 |
  | 자를 때 쓴 뼈대 | **812.1** |
  | 그림의 팔이 실제로 있는 자리 | **767** |

  그 결과 `split()` 이 아래팔에 배정한 픽셀이 **0개**다:

  | 어깨 반폭 | 위팔 | 아래팔 | 몸통 |
  |---|---|---|---|
  | 44.1px (지금) | 850 | **0** | 8,103 |
  | 12.6px | 1,972 | 1,183 | 4,090 |
  | 0.0px | 1,550 | **1,583** | 3,349 |

  **고칠 것 — 값을 새로 지어내지 마라. 두 함수를 일치시켜라.**
  `rig.joints()` 가 `comfy.figure()` 와 **같은 식**을 쓰게 한다: 방향을 인자로 받아
  옆모습이면 `sw = H*0.12`, `hw = H*0.10`, 그리고 `fr`/`fl` 로 두 팔을 앞으로 민다.
  **`comfy.figure()` 를 고치면 안 된다** — 그걸 바꾸면 밑그림을 다시 뽑아야 한다.

  **두 함수가 갈라지지 않게 하는 것이 이 항목의 절반이다.** 한쪽에 모아서 다른 쪽이
  불러 쓰게 하거나, 안 되면 **같은 값인지 검사하는 QA** 를 둔다.

  자체 QA: **새 검사 둘** —
  ① 「부품마다 뼈 반경 안의 그림 픽셀 수가 0 이 아닌가」(세 방향 전부),
  ② 「`comfy.figure()` 와 `rig.joints()` 가 같은 관절 좌표를 내는가」.

  ```
     ↓ add_ink()              ★ 옷 레이어는 레이어마다, 도구는 합친 뒤 한 번
  ```

  안 생긴다.** 그 그림을 어디서 받을지는 `CHARACTER.md` 5-c 에 두 길만 적어뒀고
  사람이 나중에 정한다.

  자체 QA: **새 검사** — 「레이어를 전부 겹친 것 == 합쳐서 구운 것」(픽셀 단위로 같아야
  한다). 엔진 쪽에서 레이어를 쌓는 것은 이 항목 범위 밖이고 `INBOX` 항목으로 넘긴다.
