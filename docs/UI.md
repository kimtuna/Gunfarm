# UI — 화면과 조작

> 플레이어가 **보는 것과 누르는 것**. 화면 흐름 · 캐릭터 커스터마이징 항목 · 조작.
>
> **`docs/DESIGN.md` 가 원본이다** — 거기에 제목과 한 줄 요약이 남아 있고,
> 이 파일은 그 세부다. **이 영역을 건드리는 바퀴만 읽는다**(`PROMPT.md`
> 「무엇을 읽을 것인가」). 여러 영역에 걸리는 규칙은 옮기지 않고 DESIGN.md 에
> 남겼다 — 예: 「아이템/오브젝트 크기 표준」, 「카메라 / 해상도」.

### 클라이언트 화면 흐름
- **메인 메뉴**: 플레이 / 설정 / 나가기 세 버튼.
- **플레이** → 캐릭터 슬롯 화면(3개 슬롯, 코어키퍼 스타일). 빈 슬롯을 고르면 캐릭터
  커스터마이징 화면으로 이동하고, 커스터마이징을 확정하면 월드가 만들어지며 입장한다.
  이미 캐릭터가 있는 슬롯을 고르면 그 캐릭터로 바로 월드에 입장한다.
- **설정** → 해상도 등 그래픽 옵션. 아래 "카메라 / 해상도" 참고.
- **나가기** → 애플리케이션 종료.
- **모든 화면에서 돌아가는 길은 Esc 하나다. 화면 안의 "뒤로" 버튼은 두지 않는다.**
  (2026-09-07 사람 결정 — 이전 2026-09-06 결정은 "뒤로 버튼 + Esc" 였다. 바꾼 이유는
  아래 「조작」의 Esc 항목 참고: 게임 안에서 Esc 가 일시정지 메뉴가 되면서, 메뉴
  화면에만 뒤로 버튼이 남으면 같은 키의 의미가 화면마다 달라진다. 갇히지 않는다는
  원래 목적은 Esc 가 모든 화면에서 동작하는 것으로 지킨다.)
  - **메뉴 화면**(캐릭터 슬롯 / 커스터마이징 / 설정)에서 Esc 는 **한 단계 위 화면으로**
    돌아간다.
  - **월드 안**에서 Esc 는 돌아가지 않고 **일시정지 메뉴**를 연다(아래 「조작」).
  - (2026-09-07, INBOX #17) 뒤로 버튼을 지운 자리에는 **"Esc — 돌아가기" 안내 글**만
    둔다(버튼이 아니라 라벨이다). 근거: 되돌아가는 유일한 길이 눈에 안 보이면 갇힌
    것처럼 느껴진다. 각 화면의 자체 QA 가 뒤로 버튼이 되살아나지 않았는지
    (이름으로도 글자로도) 함께 검사한다.

### 캐릭터 커스터마이징 항목
(2026-09-06 결정 — 이전에는 "아직 미정"이었다. 첫 캐릭터 화면을 실제로 만들어야 해서 정했다.)

- **색상 3가지**: 피부색 / 머리색 / 옷색. 각각 정해진 팔레트에서 고른다(자유 색상
  선택이 아니다 — 아래 근거).
- **머리모양**: 3~4종 중 선택.
- 이름 입력 + 확정 버튼. 확정하면 슬롯에 저장되고 월드가 만들어지며 입장한다.
- 근거: 색상 축은 "그래픽 파이프라인"의 **기준색 1개를 먼저 완성하고 나머지 색으로
  확장한다**는 규칙과 그대로 맞아떨어진다 — 기준색 세트를 만들어두면 나머지 색은
  팔레트 교체로 확장된다. 자유 색상(컬러 피커)을 주지 않는 것도 같은 이유다:
  제한 팔레트를 벗어나면 "같은 게임처럼 보이는가"(이질감 기준)가 깨진다.
- **머리모양은 모양마다 4방향 × 모든 모션 프레임이 따로 필요하다** — [DESIGN] 항목을
  쪼갤 때 이 비용을 감안할 것.

(2026-09-06 결정 — 화면을 실제로 만들면서 정한 구체값이다. `game/scripts/character_appearance.gd`
가 원본이고, 여기 표는 그 요약이다.)

- **팔레트에 담는 것은 색이 아니라 id 문자열이다.** 저장 파일에는 `light`/`black`/`grass`
  같은 id 만 들어간다 — 나중에 스프라이트를 팔레트 교체로 만들 때 그 id 가 그대로
  팔레트 키가 되고, 팔레트 색을 손봐도 기존 세이브가 안 깨진다.
  | 항목 | 선택지 |
  |---|---|
  | 피부색 (5) | 밝은 / 중간 / 구릿빛 / 짙은 / 가장 짙은 |
  | 머리색 (6) | 검정 / 갈색 / 금발 / 적갈색 / 은발 / 쪽빛 |
  | 옷색 (6) | 풀색 / 하늘색 / 흙색 / 자주색 / 잿빛 / 주홍색 |
  | 머리모양 (4) | 짧은머리 / 단발머리 / 긴머리 / 묶은머리 |
- **이름은 최대 12자**, 앞뒤 공백은 버린다. 공백뿐인 이름으로는 확정할 수 없다(확정
  버튼이 잠긴다).
- 각 항목의 **첫 번째 선택지가 기본값**이고, 좌/우 버튼이 양끝에서 되감긴다.
- (2026-09-08, INBOX #57) **선택지가 하나뿐인 항목은 좌/우 버튼을 잠근다.** 같은 날
  캐릭터 파이프라인이 바뀌면서 머리모양 시트가 한 벌(`farmer`)만 남았는데
  (`docs/CHARACTER.md` 8절), 그 상태로 화살표를 열어두면 눌러도 제자리라 **화면이
  고장 난 것처럼 보인다.** 항목을 감추지는 않는다 — 무엇을 고를 수 있는지(그리고 지금
  무엇인지)는 여전히 보여야 한다. 위 표의 「머리모양 (4)」는 **목표이지 지금 있는
  것이 아니다**: 화면은 언제나 `character_appearance.gd` 의 목록만 내놓고, 자체 QA 도
  개수가 아니라 **내놓는 것마다 시트가 있는가**를 잰다.
- **확정하면 슬롯에 저장되고 곧바로 월드로 들어간다**(위 "클라이언트 화면 흐름" 그대로).
  확정하지 않고 뒤로/Esc 로 나가면 아무것도 저장되지 않는다.
- (2026-09-06, INBOX #11) **미리보기는 실제 게임 스프라이트다**
  (`game/scripts/appearance_preview.gd`). 앞모습을 크게 하나 + 나머지 세 방향을 작게
  늘어놓는다 — 뒷모습이 없으면 「묶은머리」처럼 **뒤에서만 보이는 차이**를 확인할 수
  없다. 배율은 정수만 쓴다. **화면에서 차지하는 크기(204px / 68px)를 적어두고 배율은
  칸에서 고른다**(2026-09-07, INBOX #46 — 그전에는 배율 12배/4배를 손으로 적어뒀는데,
  캔버스가 바뀔 때마다(34 → 17 → 32px) 사람이 다시 계산해 적어야 해서 어긋나기 쉬웠다.
  지금 idle 칸 32px 에서는 **6배 / 2배**가 골라진다). 바지/신발 색은 옷색 하나에서 함께 나온다
  (팔레트를 늘리지 않고 상하의를 구분 — 아래 INBOX #13 항목 참고).
- (2026-09-06, INBOX #8) **기준색 1벌의 스프라이트가 실제로 나왔다** —
  `game/assets/sprites/player_idle_<머리모양>.png` (아트 **32px** 칸 — 34 → 17 →
  32px 로 오갔다, 아래 「아이템/오브젝트 크기 표준」 참고. **행 = 방향**
  down/left/right/up, 열 = 프레임. 지금은 idle 1프레임뿐이고 걷기는 열이 늘어난다).
  **칸 크기는 시트마다 다를 수 있다** — 2026-09-07 (INBOX #46) 에 사람이 32px 을
  게임에서 직접 보고 정하기로 하면서 **idle 만 32px 로 굽고 걷기·도구 시트는 17px 로
  두었다.** 그래서 `player_frames.gd` 는 칸 크기를 상수로 믿지 않고 **시트 높이 ÷
  방향 4개**로 시트마다 읽는다(`cell_of()`), 발밑 보정도 칸마다 다시 넣는다.
  - (2026-09-08, INBOX #47) **32px idle 을 비율부터 다시 그렸다.** 그때 목표는
    **1 : 2**(가로 16 × 세로 32)였다 — #46 은 칸만 키우고 그림은 그대로여서
    **가로 18 × 세로 28 = 1 : 1.56** 이었다. 그때는 **16 × 32** 에 머리 40% 였다.
  - (2026-09-08, INBOX #49) **같은 날 목표가 다시 바뀌었다 — 이제 기준은 사람이
    ComfyUI 로 뽑아 고른 농부 시안**(`docs/design_reference/ref_farmer_ai.png`,
    *"엄청 잘 나왔는데? 내가 원했던 거긴 해"*)이다. #47 이 1 : 2 를 보고 잡았던 값 중
    **두 개가 뒤집혔다**: 머리가 40% → **53%**(참고 자료의 머리가 14 / 28 줄 = 50% +
    목 한 줄), 그리고 **「머리가 어깨보다 넓다」를 다시 지킨다**(16 vs 12). 세로비도
    1 : 2 → **1 : 1.78**(18 × 32)이고 몸통 5 / 다리 6 / 신발 3px 다.
    **참고 자료에 있고 우리에게 없던 것**으로 **멜빵**(상의 위에 바지 재질 두 줄 —
    재질을 새로 늘리지 않는다) · **잘록한 목** · **두껍게 감싸는 관자놀이 머리** ·
    **뒷머리 결 두 갈래**가 들어갔다. 구체값과 근거는 `docs/STYLE_GUIDE.md` 3번의
    「32px idle 의 실측값」에 있다. **걷기·도구 시트 18장은 여전히 17px 이다**(#46 의
    의도된 어긋남 — 이번에도 안 고쳤다).
  - **발밑 줄도 시트마다 다르다.** 17px 시트는 아래 한 줄이 비어 있어 설계 공간의
    15.6번째 줄이지만, **32px idle 은 칸을 다 써서 발밑이 칸의 아래 모서리**다
    (`player_frames.gd` 의 `feet_y()`). 화면에서 캐릭터 96px = 지형 타일 정확히
    두 칸이고, 이제 **그림이 실제로 그 96px 를 다 채운다.**
  만드는 코드는
  `game/tools/gen_character.py` 이고, 그 안의 `palette(skin, hair, cloth)` 에 위 표의
  16진 색을 넣으면 나머지 색은 **램프만 갈아끼워** 나온다(형태를 다시 그리지 않는다).
  검증은 `game/qa/qa_player_sprite.gd`(엔진 쪽 규격·캡처)와
  `game/qa/qa_sprite_check.py`(그림 자체의 팔레트·대비·명도, `.venv/bin/python` 으로 실행).
- (2026-09-06, INBOX #13) **바지·신발 색은 옷색에서 색상(hue)까지 옮겨서 만든다.**
  옷색을 어둡게만 쓰면 상의와 하의의 색상이 같아서 몸이 기둥 하나로 뭉친다
  (`docs/STYLE_GUIDE.md` 「자연스러움」). **바지다운 색 두 개(흙빛/데님)** 중 옷색에서
  먼 쪽에 붙이고 옷색을 조금 섞는다(`gen_character.py` 의 `pants_color()`) — 옷색
  6종 어느 것을 골라도 상의와 하의가 다른 색상이 된다. 팔레트는 늘지 않는다(여전히
  옷색 하나가 셔츠/바지/신발을 정한다).
- (2026-09-06, INBOX #13) **볼 홍조(`blush`)는 피부색이 함께 정하는 한 단계짜리
  램프다** — `character_palettes.gd` 의 `SKIN` 이 피부 램프와 같이 들고 있고,
  팔레트 교체도 같이 따라간다(피부색을 바꾸면 홍조도 바뀐다).
- (2026-09-06, INBOX #9) **상의/하의를 가르는 방식은 "옷색 × 비율"이 아니라 재질별
  목표 명도다**(`gen_character.py` 의 `bands_for()`). 미리보기의 색 사각형과 달리
  스프라이트에는 음영 4단계가 들어가서, 비율로 어둡게 하면 옷색에 따라 상의와 값이
  겹치거나 반대로 신발이 외곽선보다 어두워져 검은 구멍이 됐다. 지금은 **옷색의 명도에서
  셔츠 명도를 정하고(×1.45, 138~168 로 자름) 바지 = 셔츠 × 0.70, 신발 = 셔츠 × 0.45**
  로 계단을 코드가 보장한다 — 옷색 6종 어느 것을 골라도 상의/하의/신발이 갈린다.
  `PANTS_DARKEN`/`SHOES_DARKEN` 은 이제 "무슨 색을 어둡게 쓸 것인가"(색상)만 정한다.
- **피부색·머리색에는 이 고정 밴드를 쓰지 않는다 — 하한만 준다**(피부 88, 머리 50).
  이 둘은 플레이어가 고른 색의 명도 자체가 의미이기 때문이다(금발은 밝고 검정은
  어둡다). 실제로 한 번 고정 밴드로 만들었더니 은발도 「가장 짙은」 피부도 전부 같은
  값으로 나와서 커스터마이징이 통째로 무의미해졌다.
- (2026-09-06, INBOX #11) **색은 실행 중 팔레트 교체로, 머리모양은 시트를 나눠서
  만든다.** 5(피부) × 6(머리) × 6(옷) × 4(머리모양) = 720 벌을 구워둘 수는 없다.
  - **시트는 머리모양마다 한 장**이다(형태가 다르므로 다시 그려야 한다).
    경로 규칙은 `player_frames.gd` 의 `sheet_path(모션, 머리모양)` 한 곳에만 있다.
  - **색은 PNG 픽셀의 색을 통째로 갈아끼워서** 만든다 — 기준색 램프의 색 →
    고른 색의 램프의 색(`game/scripts/character_sprite.gd`). 재질별 4단계 램프가
    한 벌로 바뀌므로 음영이 그대로 남는다. 형태는 건드리지 않는다(알파 불변).
  - 램프 색 자체는 **생성기가 뽑아준 `game/scripts/character_palettes.gd`** 에 있다
    (자동 생성 — 손으로 고치지 말 것). `make_ramp()` 를 GDScript 로 옮겨 적으면
    반드시 생성기와 어긋나므로, 계산한 값을 그대로 내려보내는 쪽을 골랐다.
    **밴드가 항목마다 독립**이라(피부 램프는 피부색만, 옷 램프는 옷색만 본다)
    5×6×6 조합이 아니라 5+6+6 줄이면 된다.
  - 기준색 램프 20색은 **서로 겹치면 안 된다** — 겹치면 "이 픽셀이 무슨 재질인가"가
    모호해져 바꿔치기가 엉뚱한 재질을 칠한다. `qa_character_sprite.gd` 가 검사한다.
  - (2026-09-08, INBOX #68) **AI 그림으로 옮겨간 뒤에도 이 구조는 그대로다** — 바뀐 것은
    「기준색 1벌을 어떻게 굽는가」뿐이다. 2026-09-08 아침에 캐릭터가 리그로 옮겨가면서
    램프가 없어져(색이 그림에 구워져 있다) 커스터마이징이 죽어 있었는데, **리그가
    부품을 알고 있으므로** 부품 + 그 부품의 대표색으로 재질을 갈라 굽기 직전에 기준색
    램프로 갈아끼운다. 절차와 「되돌리지 말 것」은 `docs/CHARACTER.md` 5-b 절에 있다.
    **게임 쪽(`character_sprite.gd` · `character_palettes.gd`)은 한 줄도 안 고쳤다** —
    없던 램프가 생긴 것뿐이다.

### 조작
- 이동: WASD
- **시야/조준 방향: 마우스로 회전.** (2026-09-07 사람이 구체화 — 기준은 덕코프다.)

    붙잡고, 그걸 넘겨야 다음 방향으로 바뀐다. 근거: 45도 경계에 마우스를 올려두면
    손이 조금만 떨려도 두 시트가 매 프레임 번갈아 나와 캐릭터가 덜덜 떤다.

    신뢰」의 "입력(이동 방향 / 조준 각도 / 버튼)만 보낸다" 그대로, 이동 방향과 같은
    입력 구조체에 담아 `player_motion.gd`(순수 클래스)가 받는다. **노드는 마우스
    좌표를 각도로 바꾸는 일까지만 하고, 그 각도를 쓰는 계산은 코어에 둔다** — 화면
    좌표는 클라이언트마다 다르지만 각도는 모두에게 같은 값이기 때문이다.
- **Esc: 월드 안에서는 일시정지 메뉴를 연다** (2026-09-07 사람 결정 — 이전에는 슬롯
  화면으로 돌아가는 키였다. 근거: 보통의 게임에서 Esc 는 나가기가 아니라 메뉴다).

    계속 움직인다. 근거: 멀티플레이에서는 한 사람이 Esc 를 눌렀다고 세계가 멈출 수
    없다 — 싱글에서만 멈추게 만들어두면 멀티를 붙이는 시점에 그 코드를 전부 다시
    쓰게 된다. 대신 **메뉴가 열린 동안 플레이어 입력만 받지 않는다**(이동/발사 입력이
    0 으로 들어간다 — 입력을 끊는 것이지 시간을 멈추는 게 아니다).
  - 메뉴 화면들에서 Esc 는 한 단계 위로 돌아간다(위 「클라이언트 화면 흐름」).
  - (2026-09-07, INBOX #17 — 실제로 만들면서 정한 구체값이다.) 일시정지 메뉴는

      메뉴를, 둘 다 없으면 일시정지 메뉴를 연다. 겹쳐 뜬 화면은 **자기 Esc 를 처리하지

    - **입력을 끊는 것은 `player.gd` 의 `input_enabled` 하나뿐이다.** 이동은 0 이 되고

#### 플레이어 이동
(2026-09-06 결정 — 플레이어를 실제로 월드에 세우면서 정한 구체값이다.
`game/scripts/player_motion.gd` 가 원본이고, 여기 표는 그 요약이다.)

| 항목 | 값 |
|---|---|
| 이동 속도 | **240 월드 단위/초** (= 타일 5칸/초) |
| 시뮬레이션 틱 | **60Hz 고정** (`TICK_DELTA` 1/60초) |
| 몸통 충돌 상자 | **18 × 10**, 원점(발밑) 기준 좌우 9 / 상하 5 |
| 이동 키 | W/A/S/D — `physical_keycode` 로 잡아 자판 배열이 달라도 같은 자리 키가 먹는다 |

- **이동 계산은 `player_motion.gd`(노드를 상속하지 않는 순수 클래스)가 한다**
  ("시뮬레이션 구조"). 노드(`player.gd`)는 **키를 읽어 -1/0/1 두 축으로 만들고 그리는
  일만** 한다 — 위 "서버 권위 / 클라이언트 신뢰"의 "클라이언트는 위치를 보내지 않는다.
  입력만 보낸다"를 나중에 붙이는 게 아니라 처음부터 지키기 위한 구조다. 그래서 코어의
  `tick()` 은 프레임 시간을 인자로 받지 않는다 — **호출 횟수가 곧 시뮬레이션 시간**이라,
  서버는 "실제 경과 시간이 허용하는 횟수"만 돌려주면 그게 그대로 속도 상한이 된다.
- **몸통 충돌 상자는 2026-09-07(INBOX #19)에 32×18 → 18×10 으로 줄었다** — 캐릭터
  캔버스가 34 → 17px 로 절반이 되면서 몸 폭도 절반이 됐기 때문이다. 어깨가 아트 7px ×
  3배 = 21 이라 상자(18)는 그보다 조금 좁다 — 해안에 비스듬히 붙었을 때 어깨가 걸리지
  않아야 한다(옛 값도 36 짜리 어깨에 32 였다).
- **한 틱 이동량(4)은 타일(48)보다 훨씬 작아야 한다.** 크면 바다 한 칸을 통째로
  건너뛴다(`docs/GOTCHAS.md`). 자체 QA 가 이 비율을 직접 검사한다.
- **대각선도 정규화한다** — 안 하면 대각으로 갈 때만 1.41배 빨라져서 대각으로만 뛰는 게
  이득이 된다.
- **충돌은 축을 따로 밀어서 판정한다.** 그래야 해안에 비스듬히 붙었을 때 붙잡히지 않고
  미끄러진다. 막히면 그 자리에서 멈추는 게 아니라 **타일 경계에 딱 붙인다** — 안 그러면
  한 틱 이동량(4px)만큼 물가에 틈이 벌어져 보인다.
- **노드의 원점은 발밑이다**(스프라이트를 `offset` 으로 올린다). 타일 점유와 나중의
  앞뒤(Y) 정렬이 자연스러우려면 몸 한가운데가 아니라 발이 기준이어야 한다.
- **카메라는 플레이어 노드의 자식이다** — 따라다니게 만드는 코드가 따로 없다. 확대/축소는
  하지 않는다(위 "카메라 / 해상도" PvP 공정성 규칙). 위치를 밖에서 볼 때는 `global_position`
  으로 본다.
- 지금 막는 것은 **바다 타일**과 **걷기를 막는 월드 오브젝트가 선 칸**(나무·바위 —
  위 「월드 오브젝트」의 「막는 것과 막는 크기」)이다. 둘을 한 물음으로 묶은 것이
  `world_gen.gd` 의 **`is_walkable()`** 이고, `blocked_at()` 은 몸통 상자가 걸치는
  칸마다 그걸 묻는다 — **앞으로 붙는 벽·건축물도 같은 자리에 덧붙인다.**
  **이건 「걸을 수 있는가」만 답하는 자리다** — 총알은 이 판정을 쓰지 않는다(물을
  통과한다, 「전투」). 총알을 막는 것은 그쪽의 `blocks_bullet` 에 따로 꽂는다.
- 검증은 `game/qa/qa_player_world.gd` — 코어(재현성/속도상한/바다충돌/미끄러짐)와
  화면(스폰 위치/발밑 정렬/WASD/카메라 추적)을 함께 본다.
