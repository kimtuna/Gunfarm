# GOTCHAS.md — 엔진/헤드리스 실행 함정

`godot --path . --script <검증스크립트>.gd`로 헤드리스에 가깝게 실행해서 스크린샷을
찍는 방식으로 자체 QA를 할 때 부딪히기 쉬운 Godot 4 엔진의 함정들이다.

> **매 바퀴 읽는 파일이 아니다.** 대부분의 바퀴는 이런 문제를 아예 안 만나니, 미리
> 읽어두는 건 낭비다. 대신 `PROMPT.md`의 지시대로, **실행 결과가 예상과 다르거나
> 에러가 났을 때** 원인을 스스로 조사하기 전에 먼저 이 파일부터 검색해서 확인한다.
>
> **이 파일에 새 항목을 추가할 때 (`PROMPT.md` 규칙 참고)**: 추가 전 중복 확인,
> "사실 한두 줄 + 대응법 한두 줄" 형식 고정, 150줄 넘으면 추가 대신 STATUS.md에
> 정리 필요 신호만 남기기 — 이 세 가지를 지킨다.

- **새 PNG를 저장만 하면 `load()`가 조용히 실패한다.** `.png.import` 메타파일이 없으면
  Godot이 못 읽는다. 새 스프라이트를 저장한 직후엔 항상
  `godot --headless --path . --import`로 강제 재임포트한 뒤 스크린샷으로 재검증할 것.
- **오토로드(전역 싱글턴)를 정적 식별자로 참조하면 `--script` 모드에서 컴파일
  에러가 난다.** `--script`는 오토로드를 컴파일러 전역 식별자로 안 올려준다.
  - 검증 스크립트 자신이 참조 → `get_root().get_node("오토로드이름")`처럼 문자열
    경로로 동적 조회.
  - 검증하려는 **씬 자체의 기존 스크립트**가 정적 참조 → 이 우회로도 안 통함.
    `project.godot`의 `[autoload]`에 검증 스크립트를 임시로 넣고 일반 실행
    (`godot --path .`, `--script` 없이)으로 띄운 뒤 끝나면 원상복구.
  - `--script` 최상단에서 `preload("res://scenes/...tscn")`으로 씬을 미리 로드해도,
    그 씬이 물고 있는 다른 스크립트들의 파싱이 오토로드 등록 전에 일어나 같은 에러가
    난다 → `_process()`에서 몇 프레임 지난 뒤 `load()`로 지연 로드할 것.
- **`add_child` 직후 `@onready` 변수는 안 채워져 있다.** NOTIFICATION_READY가 다음
  프레임에 옴 — 최소 1~2프레임 지난 뒤에 읽을 것. 오토로드에 값 넣는 것도 마찬가지다
  (오토로드의 배열/슬롯이 자신의 `_ready()`에서 초기화되는 구조라면, 트리에 들어간
  첫 프레임 이후에나 실제로 크기가 잡힌다).
- **`queue_free()`는 즉시 안 사라진다.** 스크립트로 프레임을 강제 진행시켜도
  `is_instance_valid()`는 false가 안 됨 — `is_queued_for_deletion()`으로 확인할 것.
- **`--headless`로는 화면 캡처가 안 된다**(`get_texture()`가 null). 캡처가 필요하면
  `--headless` 빼고 실제 렌더러로 띄울 것. `--headless`로 캡처를 시도하면 에러 전에
  한참 멈춘 것처럼 보일 수 있으니, 애초에 시도하지 말 것.
- **상태 설정 직후 바로 캡처하면 한 프레임 전 상태가 찍힌다.** "설정 → 2~3프레임 대기 →
  캡처" 순서를 지킬 것.
- **`get_root().get_visible_rect().size`(논리 좌표)와 실제 캡처 픽셀 크기가 다를 수
  있다**(디스플레이 배율 등). 크롭 좌표는 항상 캡처한 `Image.get_size()` 기준으로
  계산할 것.
- **`Input.warp_mouse()`가 헤드리스에 가까운 환경에서 실제 OS 커서를 못 옮길 수
  있다.** 마우스 방향을 강제로 바꿔야 하는 검증(예: 4방향 스크린샷)은
  `set_physics_process(false)`로 마우스 추종 로직을 멈추고 방향/텍스처 갱신 함수를
  직접 호출하는 방식을 우선 시도할 것.
- **Area2D/RigidBody 충돌은 `add_child` 직후 바로 확인하면 false negative가 난다.**
  최소 2~3 물리 프레임 진행 후 신호나 결과로 확인할 것.
- **캐릭터/오브젝트 이동 함수를 검증할 때 한 번에 큰 이동량을 넘기면 충돌 판정을
  건너뛸 수 있다**(벽 한 칸을 통째로 건너뜀). 실제 이동 속도에 가까운 작은 값으로
  여러 번 나눠 호출해서 실제 물리 루프를 흉내낼 것.
- **GDScript 람다는 바깥 지역변수를 값으로 캡처한다.** `bool ok=false`를 람다 안에서
  바꿔도 반영 안 됨 — `Array`/`Dictionary`(참조 타입)에 append하는 식으로 우회.
- **YSort 컨테이너 안에서는 `z_index`가 완전히 무시된다**([godotengine/godot#62715]
  (https://github.com/godotengine/godot/issues/62715)). "항상 맨 위/아래여야 하는"
  오브젝트(벽/문 등)는 YSort 밖에 두고 고정 `z_index`를 줄 것. Y좌표로 자연스럽게
  앞뒤가 갈려야 하는 것(플레이어/동물/가구류)만 YSort 안에 둘 것.
- **비슷한 색 오브젝트가 겹치는 렌더링 순서 문제는 축소 스크린샷만으로는 판정하기
  어렵다.** 코드로 특정 좌표의 픽셀 색을 직접 비교하는 자동 판정을 같이 넣을 것.
- **macOS `screencapture` 명령은 샌드박스 권한 문제로 실패할 수 있다.** 대신 Godot
  스크립트 안에서 `root.get_texture().get_image().save_png(path)`로 엔진 내부 렌더
  결과를 직접 저장하는 방식이 더 안정적이다.
- **QA 스크립트가 같은 캐릭터 슬롯/인벤토리를 재사용하면 이전 실행의 저장 상태가
  남아 거짓 실패가 날 수 있다.** 검증 시작 전에 `user://*.save`를 지우거나 관련
  데이터 구조를 초기화하고 시작할 것.
- **완료로 표시된 항목이 실제로는 불합격일 수 있다.** 미커밋 코드를 이어받아 그대로
  커밋할 때도, 완료 체크를 다시 볼 때도, 문서 표시보다 실제 스크린샷 재검증을 믿을 것.
- **에디터의 "임베디드 Game 패널" 미리보기와 실제 실행/빌드는 다르게 동작할 수
  있다.** "설정을 바꿔도 반영이 안 된다"류 문제는 먼저 에디터 Play 버튼으로 본 건지
  확인할 것 — 실제 검증은 `godot --path .`로 에디터 밖에서 해야 한다.
