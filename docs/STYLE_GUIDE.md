# STYLE_GUIDE — 도트 그림체 기준

> `[DESIGN]` 태그 항목일 때만 읽는다. `[BUILD]`는 그림을 만들지 않으니 필요 없다.
>
> 목표하는 느낌: **코어키퍼**. 스타듀밸리 계열의 따뜻한 제한 팔레트 + 또렷한 외곽선 +
> 치비 비율. 정교한 일러스트가 아니라 "작고 읽기 쉬운 도트"다.

## 1. 크기와 배율 (가장 중요 — 여기가 어긋나면 뭘 그려도 지저분해진다)

- **네이티브 캔버스 17px, 씬 스케일 3배 → 화면 51px.**
  (**2026-09-07 사람이 절반으로 낮췄다** — 이전 값은 34px → 화면 102px 이었다.
  근거와 "왜 스케일이 아니라 캔버스를 줄였는가"는 `DESIGN.md` 「아이템/오브젝트 크기
  표준」에 있다. **씬 스케일 3배는 건드리지 않는다** — 타일과 도트 크기를 맞추는
  것이 바로 이 배율이다.)
- **17px 는 34px 의 절반이 아니라 1/4 이다.** 넓이가 네 배로 줄었으니, 34px 에서
  쓰던 표현을 그대로 축소해 넣으려 하면 전부 뭉갠다. **뺄 것을 먼저 정하고 그린다** —
  아래 3번 비율표와 4번 「자연스러움」의 눈·옷 포인트 기준이 그래서 함께 바뀌었다.
- **배율은 반드시 정수여야 한다.** 1.5배 같은 소수 배율을 쓰면 화면에서 아트 픽셀
  하나가 1px, 2px, 1px, 2px… 로 들쭉날쭉해져서 도트가 뭉개져 보인다. 이게 "도트처럼
  안 보이는" 가장 흔한 원인이다.
- 타일은 **아트 16px × 3배 = 화면 48px**. 캐릭터와 아트 픽셀 크기가 같아진다.
- 도구/드롭 아이템 등 작은 것은 **아트 최소 6px**(화면 18px ≥ DESIGN.md 의 16px 하한).
  (2026-09-07 — 캐릭터를 절반으로 줄이면서 DESIGN.md 의 하한이 32px → 16px 이 됐다.)

## 2. 팔레트

- **재질마다 4단계 램프**(밝은면 → 기본 → 그늘 → 가장 어두움)를 미리 정해두고, 그
  4색 밖으로 나가지 않는다. 단계를 늘리면 도트가 물러진다.
- **외곽선은 순검정(0,0,0)을 쓰지 않는다.** 공통 잉크색 `#261C2C`(38,28,44) —
  어두운 갈보라. 순검정은 화면에서 툭 튀어나와 스타듀/코어키퍼 느낌을 깬다.
- 새 재질을 추가할 때는 기존 램프들과 **채도·명도 폭을 맞춘다.** 혼자 쨍하면 불합격.
- 커스터마이징 색(피부/머리/옷)은 **팔레트 교체**로 만든다 — 기준색으로 한 벌
  완성한 뒤 램프만 갈아끼운다. 형태를 다시 그리지 않는다.

## 3. 비율 (치비)

(2026-09-06 재조정. 사람 피드백: *"그렇게 나쁘진 않은데 예쁘지가 않다.
상체가 너무 크다. **더 짜리몽땅하게.** 상하의가 너무 단색이라서 그런 것 같기도 하다."*
목표 수준은 **코어키퍼 정도**다.)

**아래 34px 표는 폐기됐다. 2026-09-07 사람 피드백으로 캔버스가 17px 로 줄고 비율도
같이 바뀐다** — *"눈이 너무 커서 줄여주고 다리가 너무 롱다리야. … 머리 크기도 줄여줘."*
새 표는 17px 로 실제로 그려본 바퀴가 **여기에 실측값으로 다시 쓴다**(옛 표처럼
"실제로 만들어져 있는 값"이어야 한다 — 목표치를 적어두고 그림이 다르면 안 된다).

**새 표를 채울 때 지켜야 할 방향** (17px 캔버스, 캐릭터는 y 1~16 안):

| 부위 | 방향 | 왜 |
|---|---|---|
| 머리 | 전체 높이의 **47% → 40% 안팎으로 낮춘다** | 사람이 "머리 크기도 줄여줘". 다만 **어깨보다는 계속 넓어야 한다**(아래) |
| 몸통 | 머리를 줄인 만큼 **늘리지 않는다** | 「자연스러움」의 원래 피드백이 "상체가 너무 크다"였다 — 되돌리지 말 것 |
| 다리 | **짧게** — 전체에서 다리가 차지하는 비율을 옛 표(6/30 ≈ 20%)보다 더 낮춘다 | 사람이 "다리가 너무 롱다리야" |
| 신발 | 다리에 붙는 만큼 같이 줄인다 | |

- **머리가 어깨보다 넓다**가 이 비율의 핵심이다. 머리와 어깨가 비슷하면 치비가 아니라
  그냥 작은 사람으로 보인다. **머리를 줄이라는 지시는 "어깨보다 좁게"가 아니다** —
  머리를 줄이면서 어깨도 같이 좁혀서 이 관계는 유지한다.
- **뒷모습(up)은 얼굴이 보이면 안 된다** — 머리 전체가 머리카락이다.
- **17px 에서는 1px 이 옛 캔버스의 2px 이다.** 한 칸을 옮기는 것이 옛 두 칸이므로,
  옛 값을 반으로 나눈 소수를 반올림하는 식으로 표를 만들지 말고 **17px 격자 위에서
  직접 후보를 여러 개 그려 비교해서** 정한다.

### 자연스러움 — 여기가 지금 제일 약한 곳

"이질감 없음"과 "퀄리티"를 통과해도 **어색하면 불합격**이다. 실제로 나왔던 문제들이다.

- **단색을 피한다 (가장 큰 원인).** 한 재질 영역을 기본색 하나로만 칠하면 색종이를
  오려 붙인 것처럼 보인다. **재질마다 램프 4단계 중 최소 3단계를 실제로 쓰고, 어느
  한 단계가 그 영역의 70% 를 넘지 않게** 한다. 특히 상의·하의처럼 넓은 면이 그렇다.
- **상의와 하의는 서로 다른 색상(hue).** 둘 다 초록이면 몸이 한 덩어리로 뭉친다 —
  명도만 다르게 하는 것으로는 부족하다.
- **옷에 포인트를 1~2개.** 허리띠, 소매 끝 밝은 띠, 옷깃 같은 것. 없으면 옷이 아니라
  색칠한 사각형으로 읽힌다. **17px 에서는 1개까지다**(2026-09-07 — 34px 때 1~2개였다.
  넓이가 1/4 이라 두 개를 넣으면 옷이 포인트로 꽉 찬다).
- **실루엣에 긴 직선을 두지 않는다.** 외곽선에 5px 넘는 곧은 구간이 이어지면 각져
  보인다. (**이 5px/6px 는 34px 캔버스에서 잰 값이다** — 17px 에서는 캐릭터 높이의
  1/3 이라 사실상 아무것도 안 걸린다. 캔버스를 줄이는 바퀴가 같은 비율로 다시 잡을 것.) 어깨·머리 모서리를 굴린다. (걷기 시트만 **6px** 이다 — 딛고 선 다리는 그
  자체가 곧은 기둥이라, 서 있는 그림이 5px 에서 끊기는 건 두 다리가 나란하고 손이
  허벅지를 덮어서일 뿐이다. 손이 올라가는 프레임에서 그 선이 한 칸 길어진다.)
- **눈**: **2026-09-07 에 기준이 바뀌었다** — 사람이 *"눈이 너무 커서 줄여주고"*.
  옛 기준은 "최소 3×3"이었는데, 17px 캔버스에서 3×3 은 얼굴 폭의 절반을 눈 하나가
  차지하는 크기다. 새 기준: **1×2 또는 2×2** 로 하고, **하이라이트는 눈이 2×2 일
  때만 1px 넣는다**(1×2 에 하이라이트를 넣으면 눈의 절반이 흰색이 되어 눈이 아니라
  점 두 개로 읽힌다). 눈 사이는 계속 넓게(얼굴 폭의 1/3 정도) 두고, **각진 눈매·눈썹·
  기울어진 윗선을 넣지 않는다** — 째려보는 인상이 되면 다른 걸 아무리 고쳐도
  살아나지 않는다. `qa_sprite_check.py` 의 「눈」 검사는 이 값으로 다시 잡을 것
  (**상한이 생겼다는 게 핵심이다** — 옛 검사는 하한만 봐서 큰 눈을 통과시킨다).
- **머리카락은 부드러운 덩어리로.** 뾰족한 가닥을 세우지 않는다 —
  **뒷모습이 빗자루처럼 보이면 불합격.** 윗면에 밝은 하이라이트 띠를 넣는다.
- **볼 홍조** 1~2px. **입은 그리지 않는다**(작은 크기에서 지저분해진다).

**위 항목은 전부 `game/qa/qa_sprite_check.py` 가 숫자로 판정한다**(2026-09-06,
INBOX #13 — 「단색 / 색상차 / 각짐 / 비율 / 눈」). 눈으로 보기 전에 먼저 돌린다
(「작업 순서」 참고). 새로 알게 된 어색함은 여기 글로만 적지 말고 **검사로 옮긴다.**

## 4. 음영과 형태

- **광원은 왼쪽 위 고정.** 모든 자산이 같은 방향이어야 한다.
- **같은 재질끼리 맞닿는 경계(예: 팔과 몸통)에는 내부선을 넣는다.** 안 넣으면 팔이
  몸통에 녹아서 실루엣이 안 읽힌다. 내부선은 **잉크가 아니라 그 재질 램프의 가장
  어두운 색**을 쓴다 — 잉크로 그으면 캐릭터가 조각조각 잘려 보인다.
- 외곽선은 실루엣 바깥에 1px.

## 5. 도구 — 무엇이 깔려 있고 언제 쓰나

**전부 `.venv/bin/python` 으로 돌린다.** 시스템 `python3`(3.9)에는 아무것도 없다.
전부 로컬·무료라 **몇 번을 돌리든 비용이 들지 않는다** — 후보를 아끼지 말 것.

| 도구 | 무엇에 쓰나 | 언제 손이 가야 하나 |
|---|---|---|
| **Pillow** (`PIL`) | 이미지 입출력, 최종 PNG 저장, 후보 이어붙이기 | 항상 |
| **numpy** | 픽셀을 배열로 다루는 전 과정 — 높이장·법선·조명·축소·팔레트 교체 | 항상. 파이썬 이중 for 문으로 픽셀을 돌면 느리고 코드도 길어진다 |
| **scikit-image** (`skimage`) | 형태 연산 — 외곽선 추출(`segmentation.find_boundaries`), 팽창/침식(`morphology`), 라벨링(`measure.label`) | 실루엣을 다듬거나, 덩어리가 몇 개로 쪼개졌는지 **자동으로 검사**할 때 |
| **hitherdither** | 디더링 알고리즘 모음 (Bayer, Floyd-Steinberg, cluster-dot) | 제한 팔레트에서 그라데이션을 낼 때. 직접 짠 Bayer 로 부족하면 여기 것들을 비교해볼 것 |
| **pyxelate** | 이미지 → 픽셀아트 변환 (다운샘플 + 팔레트 양자화 + 외곽선) | 참고 이미지(사진/AI 생성물)의 **팔레트나 비율을 뽑아낼 때**. 이걸로 만든 결과를 게임 자산으로 쓰지는 않는다 |
| **opensimplex** | 심리스 노이즈 | 지형 타일의 얼룩, 나무껍질/돌 표면 같은 **자연스러운 무늬** |

`Draw Things.app`(로컬 Stable Diffusion)은 **사람이 참고 이미지를 만들 때만** 쓴다.
세션이 자산을 생성하는 경로가 아니다 (`CLAUDE.md` 「그림 방식」).

## 6. 권장 파이프라인

한 픽셀씩 직접 찍으면 평평해진다(테두리에만 음영이 걸림). 대신:

1. 대상을 **입체 덩어리**(구/캡슐/둥근상자)의 합으로 정의한다 — 재질 id, 높이장,
   **부위 id** 세 장을 같이 쌓는다(부위 id 는 4번의 내부선 판정에 쓴다)
2. **12배 해상도**에서 높이장의 기울기로 법선을 구해 램버트 조명 계산 (광원 왼쪽 위)
3. 네이티브 34px 로 축소 — 재질·부위는 **최빈값**, 명도는 **평균**
4. 재질별 4단계 램프로 양자화 → 내부선 → 외곽선 (순서 디더링은 켤 수 있지만 34px
   에서는 얼룩만 생겨서 기본값은 끔 — 아래 「알아낸 것」 참고)

**구현이 `game/tools/gen_character.py` 에 있다.** 그냥 돌리면 게임 자산
(`game/assets/sprites/player_<모션>_<머리모양>.png` — 지금은 idle·walk 두 모션 ×
머리모양 4종 = 8장 + Godot 이 쓸 램프 표 `game/scripts/character_palettes.gd`)을
다시 만든다. `GEN_OUT=<폴더>` 를 같이 주면
후보 비교용 이어붙인 이미지도 그 폴더에 남긴다(저장소를 더럽히지 않게).

**지형은 다른 구현이다 — `game/tools/gen_terrain.py`.** 넓게 깔리는 바닥이라
입체 덩어리가 아니라 "깨끗한 바탕 + 획 몇 개"로 그리고, 대신 **타일이 이어붙었을 때**
어떻게 보이는가(이음매·반복·해안)가 전부다. 그냥 돌리면 게임 자산
(`game/assets/sprites/terrain_tiles.png` + 램프 표 `game/scripts/terrain_palettes.gd`)을
다시 만들고, `GEN_OUT` 을 주면 섬 미리보기도 남긴다. 아래 「알아낸 것」에 지형 항목이
섞여 있는 것도 그래서다.

이 구현들에서 값을 치르고 알아낸 것들 — 고칠 때 되돌리지 말 것:

- **덩어리의 높이는 반지름에 비례해야 한다**(`ROUND`). 높이를 1 로 고정하면 가운데가
  평평한 판이 되어 테두리에만 음영이 걸린 납작한 그림이 나온다.
- **그늘은 HLS 명도를 깎아서 만들지 않는다.** HLS 로 어둡게 하면 채도가 폭발해서
  밝은 피부색이 형광 주황이 된다.
- **한 색에서 갈라져 나오는 재질들(옷→바지→신발)의 구분은 "몇 배 어둡게"가 아니라
  목표 명도로 못박는다** (`make_ramp(base, target)` + `bands_for()`, 2026-09-06
  INBOX #9). 옷색을 0.46 배로 곱해 바지를 만들었더니 옷색이 무엇이냐에 따라 상의와
  값이 겹치기도 하고 신발이 잉크보다 어두워지기도 했다. **어두워질수록 채도를 살짝
  올려야** 그늘이 진흙색이 안 된다.
- **단, 플레이어가 직접 고른 색(피부·머리)에는 목표 명도를 못박지 말고 하한만 준다.**
  금발은 밝고 검정은 어둡다는 게 그 선택의 내용이다 — 고정 밴드를 씌웠더니 은발도
  가장 짙은 피부도 전부 같은 값으로 나와서 커스터마이징이 통째로 무의미해졌다.
  **이건 검사 스크립트가 못 잡는다**(한 벌만 보면 멀쩡하다) — 팔레트를 갈아끼우는
  코드를 고쳤으면 색 조합 몇 개를 실제로 뽑아 나란히 놓고 볼 것.
- **어떤 재질의 램프도 잉크(외곽선) 명도 아래로 내려가면 안 된다**(`FLOOR`). 내려가면
  그 재질은 색이 아니라 **구멍**으로 읽힌다 — 검정 머리도 예외가 아니고, 대신 램프
  폭을 넓혀서 **광택 단차**로 형태를 만든다. 검사: `qa_sprite_check.py` 의 「잉크아래」.
- **뒷모습 머리에는 결이 있어야 머리카락으로 읽힌다** — 매끈한 타원 하나면 회색
  달걀(=민머리/헬멧)이 된다. 헤어라인을 물결지게 하는 쪽은 덤불처럼 보여서 버렸다.
  **부위 id 만 다른 덩어리를 얹어** 그 경계에 내부선이 들어가게 하는 쪽이 맞는데,
  **그 덩어리를 폭이 일정한 세로 띠로 하면 안 된다**(2026-09-06, INBOX #13) —
  곧은 세로선 몇 개가 나란히 그이면 머리가 아니라 **빗자루**로 보인다. 아래로
  갈수록 벌어지는 둥근 갈래(`_fall_shape`)라야 경계가 휘어서 결로 읽힌다.
- **내부선은 경계의 오른쪽/아래에 찍는다** — 광원이 왼쪽 위이므로 그늘이 지는 쪽이다.
  반대쪽에 찍으면 밝은 면에 선이 그어져 형태가 거꾸로 읽힌다.
- **덧붙이는 혹은 `blend="max"` 로 얹는다.** 덮어쓰면 덩어리 안쪽의 높은 부분이
  혹의 낮은 높이로 눌려서 평평해진다.
- **디더링은 0 이 낫다**(34px 기준). 순서 디더링을 켜면 몸통 같은 넓은 면에 얼룩이
  생겨서 오히려 지저분해 보인다.
- **램프 맨 위에도 한계(`CEIL`)를 둔다.** 램프 배율은 기준색(검정 머리)에 맞춰 잡혀
  있어서, 금발·은발처럼 원래 밝은 색에 곱하면 목표 명도가 255 를 넘는다. 그러면
  `set_luma()` 가 모자란 만큼 흰색을 섞어 채워서 **밝은면이 순백 덩어리**가 되고,
  색을 골랐는데 하이라이트만 보면 금발과 은발이 똑같아진다(2026-09-06, INBOX #11).
- **머리단·꼬리처럼 머리 껍데기 밖으로 나가는 것은 폭이 일정한 상자로 만들지 않는다.**
  `rbox` 로 붙이면 판자/막대기로 보인다 — 아래로 갈수록 좁아지고 끝이 둥근 기둥
  (`_fall_shape`)이나 위아래가 뾰족한 타원(`_tail`)이라야 머리카락으로 읽힌다.
  그리고 **반드시 껍데기와 겹치게 시작해야** 실루엣이 한 덩어리로 남는다.
- **묶은 꼬리는 머리 실루엣 밖으로 나와야 읽힌다.** 실루엣 안에 두면 같은 색이라
  앞머리와 한 덩어리가 되어 바가지머리로 보인다(실제로 한 번 그렇게 나왔다).
- **지형 타일은 "타일 하나가 스스로 이음매 없이 감기게" 만들고, 변주는 좌표
  해시로 고른다**(2026-09-06, INBOX #12). 3×3 블록을 통째로 심리스로 굽고
  `x%3` 으로 고르는 쪽도 이음매는 완벽하지만, **눈에 띄는 무늬가 일정 간격으로
  정확히 되풀이돼서 풀밭이 벽지로 보인다.** 해시로 고르면 그 격자가 사라진다.
- **바탕이 깨끗해야 얹은 획이 무늬로 읽힌다.** 지형을 노이즈 얼룩으로 채운 후보는
  전부 위장무늬처럼 보였다 — 바탕은 기본 단계 한 색으로 두고 **획 몇 개만** 얹는
  쪽이 훨씬 낫다. 풀은 **사이를 띄운 세로 획 2~3장**(붙여 그리면 작은 삼각형 =
  멀리 있는 나무가 된다), 물결은 **가로 획**이다.
- **타일 경계를 넘는 해안선을 흔들려면 잡음의 주기가 타일 한 칸이어야 한다** —
  그래야 잡음이 월드 좌표의 함수가 되어 따로 구운 이웃 타일끼리 이어진다. 대신
  **세게 주면 안 된다**: 곧게 뻗은 해안에 같은 물결이 타일마다 정확히 되풀이돼서
  레이스 장식처럼 보인다. 해안의 변화는 잡음이 아니라 **이웃 배치(마스크)에서**
  나오게 하고, 계단은 거리장을 흐려서(가우시안) 뭉갠다.
- **그림의 지형이 논리 타일보다 작아지면 "물 위를 걷는" 것처럼 보인다.** 충돌은
  타일 단위이므로, 해안선을 흔들 때는 **땅이 커지는 쪽으로 치우치게** 하고 남은
  잠식 폭은 땅쪽 테두리선 안에 숨긴다.
- **넓은 면(지형)의 테두리에 순수 잉크를 쓰지 않는다.** 캐릭터의 1px 외곽선과 달리
  지형 테두리는 면적이 넓어서, 잉크로 두르면 지도에 매직으로 선을 그은 것처럼
  튄다 — 그 재질 램프를 잉크 쪽으로 민 색을 쓴다.
- **상의와 하의는 색상(hue)까지 갈라놓는다** (2026-09-06, INBOX #13). 옷색을 그냥
  어둡게 쓰면 몸이 초록 기둥 하나로 뭉친다. 그렇다고 **색상환을 고정 각도로 돌리면**
  옷색에 따라 형광 분홍 바지가 나온다 — **바지다운 색 두 개(흙빛/데님)** 를 두고
  옷색에서 먼 쪽에 붙인 뒤 옷색을 조금만 섞는다(`pants_color()`). 팔레트는 늘지
  않는다(여전히 옷색 하나에서 셔츠/바지/신발이 나온다).
- **큰 머리를 완전한 원으로 만들지 않는다.** 지름 14px 짜리 원은 가운데가 거의
  수직이라 옆선이 7~8줄 내리 같은 자리에 놓여 각져 보인다. **위아래 지수를 따로 준
  초타원**(`head_shape`, 위 1.6 / 아래 2.4)이면 정수리가 좁아지고 턱은 넓게 남는다.
  아래도 2 미만으로 하면 **턱이 뾰족해져서 목처럼 보인다.**
- **걷기 프레임은 팔다리를 통째로 옮기지 말고 어깨/엉덩이에서 꺾는다**(2026-09-07,
  INBOX #15). 다리를 통째로 x 로 옮기면 엉덩이가 몸통 밖으로 빠져나가고, 무엇보다
  다리 옆선이 그 길이만큼 완전한 수직선으로 남는다(「각짐」). `_fall_shape` 의
  `slant` 로 **위는 붙잡고 아래만** 보낸다.
- **옆모습 걷기는 두 다리를 한 자리에 포갠 뒤 앞뒤로만 벌린다.** idle 처럼 좌우로
  벌려 둔 채 흔들면 한쪽 착지에서 두 다리가 정확히 겹치고 반대쪽 착지에서만 벌어져서
  **한 걸음은 있고 한 걸음은 없는 절뚝**이 된다. 그리고 **먼 쪽 다리를 먼저 그리고
  한 단계 어둡게** 해야 앞뒤가 갈린다 — 순서를 안 뒤집으면 뒤쪽 다리가 앞쪽을 덮어
  실루엣이 조각조각 끊겨 보인다.
- **딛고 선 발은 몸 아래에서 뒤로 끌려야 한다**(`stance_drag`). 제자리 걷기라 몸이
  안 나가므로, 딛은 발이 뒤로 밀리지 않으면 통과 자세에서 두 다리가 정확히 겹쳐
  **폭 3px 짜리 외다리**가 되고 그 옆선이 9줄 곧게 이어진다.
- **앞/뒷모습 다리는 `cos` 으로 좌우로 흔들지 않는다.** 한쪽 착지에서 모이고 반대쪽에서
  벌어져 **제자리 뜀뛰기**가 된다(두 착지가 대칭이 아니다). 앞뒤 움직임은 어차피 안
  보이므로 **뜬 발만 안쪽으로 조금 당긴다** — 그러면 두 착지가 저절로 대칭이 된다.
- **발을 드는 곡선은 sin 그대로가 아니라 제곱이다.** sin 그대로면 착지에서도 발이
  절반쯤 떠 있어서 두 발이 같이 땅에 닿는 프레임이 하나도 없다 — 걷는 게 아니라
  제자리 행진이다.
- **몸이 가라앉는 깊이(bob)는 정수 픽셀로 끊는다.** 0.6px 처럼 어중간하게 내리면
  머리·몸통은 반 칸만 내려가는데 **눈은 격자에 찍히느라 한 칸 내려가서** 눈의 아랫줄이
  턱/옆머리로 밀려 3×3 이 2줄로 깎인다(단발 시트가 실제로 그랬다). 도트에서 몸통이
  반 칸 움직이면 음영도 매 프레임 다시 양자화되어 어른거린다.
- **위상을 고르게 뽑는다 — 반 칸 밀지 않는다.** 6프레임을 `(i+0.5)/6` 로 뽑으면
  가운데 두 프레임이 서로 거의 같은 그림이 되어 **여섯 장 중 넉 장만 쓰는 셈**이 되고,
  남은 자리에서 한꺼번에 건너뛴다. `i/6` 이면 여섯 자세가 전부 다르고 변화량도 고르다.
- **팔·다리·머리단은 폭이 일정한 상자로 두지 않는다** — 옆선이 그 길이만큼 완전한
  수직선이 된다(「각짐」). 어깨→손목으로 좁아지며 몸 쪽으로 기울이고, 허벅지→발목도
  가늘게, 긴 머리단은 좌우로 한 번 굼실거리게(`wave`) 한다. **신발은 발목보다 넓게**
  만들어 다리에서 발로 이어지던 선을 한 칸 꺾는다.
- **눈은 통짜 잉크 3×3 으로 만들면 선글라스가 된다.** 바깥쪽 한 줄을 흰자
  (하이라이트)로 비워야 눈망울로 읽힌다(`EYE_ART` 의 `stripe`).
- **옆모습 코는 눈보다 아래(광대 높이)에 둔다.** 눈높이에 두면 1px 돌기가 요정 귀로
  보인다. 대신 **실루엣 밖으로 한 칸은 확실히 나와야** 한다 — 안 나오면 얼굴 앞선이
  6줄 곧게 이어진다.
- **넓은 머리단이 눈을 덮으면 안 된다.** 단발처럼 폭이 넓은 머리단은 **눈보다 아래
  (광대)에서 시작**하게 해야 얼굴이 열린다(`ftop`). 폭을 줄여서 피하면 긴머리와
  구별이 안 된다.
- **머리 길이가 다른 시트는 「평균명도/어두운비율/채도」가 실제로 다르다.** 기준색
  머리가 검정(무채색)이라 길수록 어둡고 탁해진다 — `qa_sprite_check.py` 의 SPECS 에서
  **그 셋만** 시트마다 따로 잡는다. 나머지 검사는 늦추지 않는다.

## 7. 작업 순서 — **먼저 검사 스크립트를 돌리고, 통과했을 때만 눈으로 본다**

**한 번 뽑고 끝내는 것이 이 항목에서 가장 흔한 실패다.** 그런데 매 후보를 눈으로만
보면 한 바퀴에 이미지를 수십 장 읽게 되고, 그 비용 때문에 오히려 후보를 적게 뽑게
된다. 그래서 **기계가 판정할 수 있는 것은 먼저 코드로 거른다**(2026-09-06, INBOX #9):

```
.venv/bin/python game/qa/qa_sprite_check.py [PNG ...]     # 불합격이면 종료 코드 1
```

이 스크립트가 보는 것(캐릭터 시트): 규격 / 반투명 픽셀 / 팔레트 램프 밖의 색 /
재질끼리 색 충돌 / **램프가 잉크(외곽선)보다 어두워지지 않는지** / 순검정 / 외곽선 /
실루엣 조각 / **맞닿은 재질의 경계 명도차** / 평균 명도·명암폭·어두운 비율·채도 /
방향 4개의 바운딩박스. **그리고 위 「자연스러움」 절 전체**(2026-09-06, INBOX #13):
**단색**(램프 단계를 몇 개나 쓰는가, 한 단계가 70% 를 넘는가) / **색상차**(상의·하의
hue) / **각짐**(실루엣 옆선·윗선의 곧은 구간 5px 상한 — 아랫변은 발바닥이라 뺀다) /
**비율**(머리 비율 / 몸통·다리·신발 높이 / 머리 폭 > 어깨+팔 폭) / **눈**(크기 상한과
하한, 피부에 둘러싸인 잉크 덩어리만 눈으로 센다).
**이 두 검사의 구체적인 수치는 2026-09-07 캔버스 축소(34px → 17px)로 전부 다시
잡아야 한다** — 위 3번 비율표와 4번 「눈」 참고.

**프레임이 여러 장인 시트(걷기 등)는 「이어짐」이 더 붙는다**(2026-09-07, INBOX #15):
프레임수(4~6) / **이어짐**(연속한 두 프레임 사이에 몸 픽셀이 얼마나 바뀌는가 — 크면
순간이동, 작으면 그 프레임이 죽어 있다) / **고르게**(가장 큰 변화 ÷ 가장 작은 변화) /
자리(실루엣이 칸 안에서 미끄러지지 않는지) / **이음**(idle 첫 프레임 → 이 시트 첫
프레임이 걷기 안의 가장 큰 변화보다 크게 벌어지지 않는지). **몸 전체가 1px 통짜로
움직인 몫은 빼고 잰다** — 걷기는 착지마다 몸이 한 칸 가라앉는데 그 한 칸만으로 몸
픽셀의 절반 넘게 값이 바뀌어서, 그대로 재면 정상적인 바운스가 "순간이동"으로 잡히고
정작 보려던 팔다리의 움직임이 그 잡음에 묻힌다.

**지형 타일 시트는 갈래가 다르다**(스펙의 `kind`): 규격 / 팔레트 / **이음매**(같은
지형을 넓게 깔았을 때 타일 경계의 명도차가 안쪽보다 크지 않은지 — 격자가 비치면
여기서 숫자로 잡힌다) / 변주가 실제로 서로 다른지 / **캐릭터가 그 위에서 묻히지
않는지**(풀과 기준색 셔츠의 명도차).

새 자산을 만들면 `qa_sprite_check.py` 의 `SPECS` 에 그 시트를 등록한다 — 등록되지
않은 PNG 는 검사 자체가 불합격 처리된다. 팔레트는 **베껴 적지 말고 생성기에서
그대로 불러온다**(`SPECS[...]["palette"]`); 손으로 옮겨 적으면 반드시 어긋난다.

반복 절차:

1. 파라미터를 바꾼 **후보를 여러 개** 생성한다 (비율, 램프, 광원 세기, 디더 강도)
2. **후보마다 `qa_sprite_check.py` 를 먼저 돌린다.** 불합격이면 눈으로 볼 것도 없이
   숫자를 보고 파라미터를 고쳐 1번으로 — 여기서 대부분의 후보가 걸러진다
3. 통과한 후보들만 **한 장에 가로로 이어붙여** 저장한다 — 나란히 놓지 않으면 차이가
   안 보인다
4. 그 PNG 를 **Read 도구로 직접 본다.** "검사를 통과했다"와 "보기 좋다"는 다른 문제다 —
   검사는 불합격을 걸러낼 뿐, 합격을 보증하지 않는다
5. 6배쯤 확대한 것과 **실제 게임 크기(3배)** 를 둘 다 본다 — 확대해서 예뻐도 실제
   크기에서 뭉개지는 경우가 많다
6. **기존 자산과 나란히 놓고** 팔레트·픽셀 크기·외곽선이 어울리는지 본다. 캐릭터는
   `game/qa/qa_player_sprite.gd` 를 `--headless` 없이 돌리면 실제 지형 색 위에 3배로
   띄운 캡처가 `user://qa_shots/` 에 남는다
7. 만족스럽지 않으면 1번으로. 만족스러우면 다음으로

**눈으로 본 뒤 새로 알게 된 불합격 조건은 되도록 `qa_sprite_check.py` 에 검사로
옮긴다** — 그래야 다음 바퀴가 같은 것을 눈으로 다시 찾지 않는다.

## 8. Godot 에 넣기

- PNG 는 `game/assets/sprites/` 에 저장한다.
- **저장 직후 반드시 재임포트한다** — 안 하면 옛 이미지가 그대로 로드된다:
  `/Applications/Godot.app/Contents/MacOS/Godot --headless --path game --import`
- 캐릭터는 `AnimatedSprite2D` + `SpriteFrames`(방향별 애니메이션)로 쓴다
  (`DESIGN.md` 「캐릭터 애니메이션」).
- **텍스처 필터는 nearest 여야 한다** — 이미 `project.godot` 에
  `default_texture_filter=0` 으로 잡혀 있다. 이게 풀리면 도트가 흐려진다.
- `*.png.import` 파일은 커밋한다 (`CLAUDE.md` 「git」).
- 화면 캡처는 `--headless` 로는 안 된다 — 다른 함정은 `docs/GOTCHAS.md` 를 볼 것.

## 9. 합격 기준

`DESIGN.md` 「그래픽 파이프라인」의 **"이질감이 없는가"**(어울림 + 자연스러움)를
그대로 따른다. 여기에 이 문서의 것을 더한다:

- [ ] **`qa_sprite_check.py` 가 통과하는가** — 아래 기계 판정 항목들은 여기서 끝난다.
      불합격이면 눈으로 볼 단계가 아니다
- [ ] **누가 봐도 "퀄리티 좋다"는 말이 나오는가** — 이게 멈추는 시점이다. 미달이면
      커밋하지 말고 미완료로 두고 `docs/STATUS.md` 에 어디가 부족한지 남긴다
- [ ] 배율이 정수인가 (아트 픽셀이 화면에서 균일한가)
- [ ] 팔레트 램프 밖의 색이 섞이지 않았는가 (검사가 봄)
- [ ] 외곽선이 순검정이 아닌가 (검사가 봄)
- [ ] 광원 방향이 기존 자산과 같은가
- [ ] **자연스러운가** — 단색으로 뭉친 면이 없는가, 상하의 색상이 다른가, 옷에
      포인트가 있는가, 실루엣에 긴 직선이 없는가, 눈에 흰 하이라이트가 있는가
      (위 「자연스러움」 절 — 상당수는 `qa_sprite_check.py` 가 잡아준다)
- [ ] **비율이 짜리몽땅한가** — 머리가 전체의 약 48%, 어깨보다 넓은가
- [ ] 실루엣만 봤을 때 부위가 구분되는가 (내부선)
- [ ] 기존 자산 몇 개와 **실제로 나란히 놓고** 비교했는가

## 10. 참고 이미지

`docs/design_reference/` 에 둔다.

- `player_idle_x6.png` — 실제로 게임에 들어간 플레이어 idle 4방향을 6배로 키운 것
  (INBOX #8, 2026-09-06). **지금 자산의 기준선이다** — 새로 만드는 것은 이것과 같은
  팔레트·같은 도트 크기·같은 외곽선이어야 한다. 더 나은 결과가 나오면 갈아끼운다.
  원본은 `game/assets/sprites/player_idle_short.png`, 만든 코드는
  `game/tools/gen_character.py`.
- `player_hairstyles_x6.png` — 머리모양 4종(짧은/단발/긴/묶은) × 4방향을 6배로 키운 것
  (INBOX #11, 2026-09-06). 새 머리모양이나 새 모션을 만들 때 **네 개가 서로 같은
  캐릭터로 보이는지** 여기에 나란히 놓고 본다.
- `player_walk_x6.png` — 걷기 6프레임 × 4방향을 6배로 키운 것, **맨 왼쪽 칸이 idle**
  (INBOX #15, 2026-09-07). 새 모션(도구 사용 등)을 만들 때 **idle 에서 그 모션으로
  넘어갈 때 자세가 뚝 끊기는지** 여기에 나란히 놓고 본다.
- `terrain_coast_x3.png` — 실제 게임 화면(3배)에서 해안 + 그 위에 선 캐릭터를
  잘라낸 것 (INBOX #12, 2026-09-06). **지형과 캐릭터가 같은 그림으로 보이는지**의
  기준선이다 — 새 지형/오브젝트는 이 팔레트·도트 크기·테두리 세기에 맞춘다.
  만든 코드는 `game/tools/gen_terrain.py`, 캡처는 `game/qa/qa_terrain_view.gd`.
- 코어키퍼풍 참고 이미지는 사람이 로컬 `Draw Things.app` 으로 만들어 넣기로 했다.
  아직 없으므로 그때까진 위 기준만으로 판단한다.
- **AI 생성물을 게임 자산으로 쓰지 않는다** (`CLAUDE.md` 「그림 방식」 참고).
