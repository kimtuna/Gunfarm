# STYLE_GUIDE — 도트 그림체 기준

> `[DESIGN]` 태그 항목일 때만 읽는다. `[BUILD]`는 그림을 만들지 않으니 필요 없다.
>
> 목표하는 느낌: **코어키퍼**. 스타듀밸리 계열의 따뜻한 제한 팔레트 + 또렷한 외곽선 +
> 치비 비율. 정교한 일러스트가 아니라 "작고 읽기 쉬운 도트"다.

## 1. 크기와 배율 (가장 중요 — 여기가 어긋나면 뭘 그려도 지저분해진다)

- **네이티브 캔버스 34px, 씬 스케일 3배 → 화면 102px.**
- **배율은 반드시 정수여야 한다.** 1.5배 같은 소수 배율을 쓰면 화면에서 아트 픽셀
  하나가 1px, 2px, 1px, 2px… 로 들쭉날쭉해져서 도트가 뭉개져 보인다. 이게 "도트처럼
  안 보이는" 가장 흔한 원인이다.
- 타일은 **아트 16px × 3배 = 화면 48px**. 캐릭터와 아트 픽셀 크기가 같아진다.
- 도구/드롭 아이템 등 작은 것은 **아트 최소 11px**(화면 33px ≥ DESIGN.md 의 32px 하한).

## 2. 팔레트

- **재질마다 4단계 램프**(밝은면 → 기본 → 그늘 → 가장 어두움)를 미리 정해두고, 그
  4색 밖으로 나가지 않는다. 단계를 늘리면 도트가 물러진다.
- **외곽선은 순검정(0,0,0)을 쓰지 않는다.** 공통 잉크색 `#261C2C`(38,28,44) —
  어두운 갈보라. 순검정은 화면에서 툭 튀어나와 스타듀/코어키퍼 느낌을 깬다.
- 새 재질을 추가할 때는 기존 램프들과 **채도·명도 폭을 맞춘다.** 혼자 쨍하면 불합격.
- 커스터마이징 색(피부/머리/옷)은 **팔레트 교체**로 만든다 — 기준색으로 한 벌
  완성한 뒤 램프만 갈아끼운다. 형태를 다시 그리지 않는다.

## 3. 비율 (치비)

34px 캔버스 기준, 캐릭터는 y 2~31 을 쓴다:

| 부위 | 세로 범위 | 비고 |
|---|---|---|
| 머리 | 2 ~ 15 | 지름이 몸통 높이와 비슷하다 — 머리가 크지만 몸이 뭉개지진 않는다 |
| 몸통 | 15 ~ 24 | 어깨가 머리보다 살짝 좁다 |
| 다리 | 24 ~ 29 | |
| 신발 | 29 ~ 31 | |

- 눈은 2×2 픽셀 잉크 두 개. 입은 그리지 않는다(작은 크기에서 지저분해진다).
- **뒷모습(up)은 얼굴이 보이면 안 된다** — 머리 전체가 머리카락이다.

## 4. 음영과 형태

- **광원은 왼쪽 위 고정.** 모든 자산이 같은 방향이어야 한다.
- **같은 재질끼리 맞닿는 경계(예: 팔과 몸통)에는 내부선을 넣는다.** 안 넣으면 팔이
  몸통에 녹아서 실루엣이 안 읽힌다. 내부선은 **잉크가 아니라 그 재질 램프의 가장
  어두운 색**을 쓴다 — 잉크로 그으면 캐릭터가 조각조각 잘려 보인다.
- 외곽선은 실루엣 바깥에 1px.

## 5. 도구 — 무엇이 깔려 있고 언제 쓰나

**전부 `.venv/bin/python` 으로 돌린다.** 시스템 `python3`(3.9)에는 아무것도 없다.
전부 로컬·무료라 **몇 번을 돌리든 비용이 들지 않는다** — 후보를 아끼지 말 것.

| 도구 | 무엇에 쓰나 | 언제 손이 가야 하나 |
|---|---|---|
| **Pillow** (`PIL`) | 이미지 입출력, 최종 PNG 저장, 후보 이어붙이기 | 항상 |
| **numpy** | 픽셀을 배열로 다루는 전 과정 — 높이장·법선·조명·축소·팔레트 교체 | 항상. 파이썬 이중 for 문으로 픽셀을 돌면 느리고 코드도 길어진다 |
| **scikit-image** (`skimage`) | 형태 연산 — 외곽선 추출(`segmentation.find_boundaries`), 팽창/침식(`morphology`), 라벨링(`measure.label`) | 실루엣을 다듬거나, 덩어리가 몇 개로 쪼개졌는지 **자동으로 검사**할 때 |
| **hitherdither** | 디더링 알고리즘 모음 (Bayer, Floyd-Steinberg, cluster-dot) | 제한 팔레트에서 그라데이션을 낼 때. 직접 짠 Bayer 로 부족하면 여기 것들을 비교해볼 것 |
| **pyxelate** | 이미지 → 픽셀아트 변환 (다운샘플 + 팔레트 양자화 + 외곽선) | 참고 이미지(사진/AI 생성물)의 **팔레트나 비율을 뽑아낼 때**. 이걸로 만든 결과를 게임 자산으로 쓰지는 않는다 |
| **opensimplex** | 심리스 노이즈 | 지형 타일의 얼룩, 나무껍질/돌 표면 같은 **자연스러운 무늬** |

`Draw Things.app`(로컬 Stable Diffusion)은 **사람이 참고 이미지를 만들 때만** 쓴다.
세션이 자산을 생성하는 경로가 아니다 (`CLAUDE.md` 「그림 방식」).

## 6. 권장 파이프라인

한 픽셀씩 직접 찍으면 평평해진다(테두리에만 음영이 걸림). 대신:

1. 대상을 **입체 덩어리**(구/캡슐/둥근상자)의 합으로 정의한다 — 재질 id, 높이장,
   **부위 id** 세 장을 같이 쌓는다(부위 id 는 4번의 내부선 판정에 쓴다)
2. **12배 해상도**에서 높이장의 기울기로 법선을 구해 램버트 조명 계산 (광원 왼쪽 위)
3. 네이티브 34px 로 축소 — 재질·부위는 **최빈값**, 명도는 **평균**
4. 재질별 4단계 램프로 양자화 → 내부선 → 외곽선 (순서 디더링은 켤 수 있지만 34px
   에서는 얼룩만 생겨서 기본값은 끔 — 아래 「알아낸 것」 참고)

**구현이 `game/tools/gen_character.py` 에 있다.** 그냥 돌리면 게임 자산
(`game/assets/sprites/player_idle.png`)을 다시 만든다. `GEN_OUT=<폴더>` 를 같이 주면
후보 비교용 이어붙인 이미지도 그 폴더에 남긴다(저장소를 더럽히지 않게).

이 구현에서 값을 치르고 알아낸 것들 — 고칠 때 되돌리지 말 것:

- **덩어리의 높이는 반지름에 비례해야 한다**(`ROUND`). 높이를 1 로 고정하면 가운데가
  평평한 판이 되어 테두리에만 음영이 걸린 납작한 그림이 나온다.
- **그늘은 HLS 명도를 깎아서 만들지 않는다.** HLS 로 어둡게 하면 채도가 폭발해서
  밝은 피부색이 형광 주황이 된다.
- **한 색에서 갈라져 나오는 재질들(옷→바지→신발)의 구분은 "몇 배 어둡게"가 아니라
  목표 명도로 못박는다** (`make_ramp(base, target)` + `bands_for()`, 2026-09-06
  INBOX #9). 옷색을 0.46 배로 곱해 바지를 만들었더니 옷색이 무엇이냐에 따라 상의와
  값이 겹치기도 하고 신발이 잉크보다 어두워지기도 했다. **어두워질수록 채도를 살짝
  올려야** 그늘이 진흙색이 안 된다.
- **단, 플레이어가 직접 고른 색(피부·머리)에는 목표 명도를 못박지 말고 하한만 준다.**
  금발은 밝고 검정은 어둡다는 게 그 선택의 내용이다 — 고정 밴드를 씌웠더니 은발도
  가장 짙은 피부도 전부 같은 값으로 나와서 커스터마이징이 통째로 무의미해졌다.
  **이건 검사 스크립트가 못 잡는다**(한 벌만 보면 멀쩡하다) — 팔레트를 갈아끼우는
  코드를 고쳤으면 색 조합 몇 개를 실제로 뽑아 나란히 놓고 볼 것.
- **어떤 재질의 램프도 잉크(외곽선) 명도 아래로 내려가면 안 된다**(`FLOOR`). 내려가면
  그 재질은 색이 아니라 **구멍**으로 읽힌다 — 검정 머리도 예외가 아니고, 대신 램프
  폭을 넓혀서 **광택 단차**로 형태를 만든다. 검사: `qa_sprite_check.py` 의 「잉크아래」.
- **뒷모습 머리는 세로 결을 넣어야 머리카락으로 읽힌다.** 매끈한 타원 하나면 회색
  달걀(=민머리/헬멧)이 된다. 헤어라인을 물결지게 하는 쪽은 덤불처럼 보여서 버렸고,
  **부위 id 만 다른 같은 껍데기를 세로로 몇 줄 얹어** 그 경계에 내부선이 들어가게
  하는 쪽이 훨씬 낫다.
- **내부선은 경계의 오른쪽/아래에 찍는다** — 광원이 왼쪽 위이므로 그늘이 지는 쪽이다.
  반대쪽에 찍으면 밝은 면에 선이 그어져 형태가 거꾸로 읽힌다.
- **덧붙이는 혹은 `blend="max"` 로 얹는다.** 덮어쓰면 덩어리 안쪽의 높은 부분이
  혹의 낮은 높이로 눌려서 평평해진다.
- **디더링은 0 이 낫다**(34px 기준). 순서 디더링을 켜면 몸통 같은 넓은 면에 얼룩이
  생겨서 오히려 지저분해 보인다.

## 7. 작업 순서 — **먼저 검사 스크립트를 돌리고, 통과했을 때만 눈으로 본다**

**한 번 뽑고 끝내는 것이 이 항목에서 가장 흔한 실패다.** 그런데 매 후보를 눈으로만
보면 한 바퀴에 이미지를 수십 장 읽게 되고, 그 비용 때문에 오히려 후보를 적게 뽑게
된다. 그래서 **기계가 판정할 수 있는 것은 먼저 코드로 거른다**(2026-09-06, INBOX #9):

```
.venv/bin/python game/qa/qa_sprite_check.py [PNG ...]     # 불합격이면 종료 코드 1
```

이 스크립트가 보는 것: 규격 / 반투명 픽셀 / 팔레트 램프 밖의 색 / 재질끼리 색 충돌 /
**램프가 잉크(외곽선)보다 어두워지지 않는지** / 순검정 / 외곽선 / 실루엣 조각 /
**맞닿은 재질의 경계 명도차** / 평균 명도·명암폭·어두운 비율·채도 / 방향 4개의 바운딩박스.

새 자산을 만들면 `qa_sprite_check.py` 의 `SPECS` 에 그 시트를 등록한다 — 등록되지
않은 PNG 는 검사 자체가 불합격 처리된다. 팔레트는 **베껴 적지 말고 생성기에서
그대로 불러온다**(`SPECS[...]["palette"]`); 손으로 옮겨 적으면 반드시 어긋난다.

반복 절차:

1. 파라미터를 바꾼 **후보를 여러 개** 생성한다 (비율, 램프, 광원 세기, 디더 강도)
2. **후보마다 `qa_sprite_check.py` 를 먼저 돌린다.** 불합격이면 눈으로 볼 것도 없이
   숫자를 보고 파라미터를 고쳐 1번으로 — 여기서 대부분의 후보가 걸러진다
3. 통과한 후보들만 **한 장에 가로로 이어붙여** 저장한다 — 나란히 놓지 않으면 차이가
   안 보인다
4. 그 PNG 를 **Read 도구로 직접 본다.** "검사를 통과했다"와 "보기 좋다"는 다른 문제다 —
   검사는 불합격을 걸러낼 뿐, 합격을 보증하지 않는다
5. 6배쯤 확대한 것과 **실제 게임 크기(3배)** 를 둘 다 본다 — 확대해서 예뻐도 실제
   크기에서 뭉개지는 경우가 많다
6. **기존 자산과 나란히 놓고** 팔레트·픽셀 크기·외곽선이 어울리는지 본다. 캐릭터는
   `game/qa/qa_player_sprite.gd` 를 `--headless` 없이 돌리면 실제 지형 색 위에 3배로
   띄운 캡처가 `user://qa_shots/` 에 남는다
7. 만족스럽지 않으면 1번으로. 만족스러우면 다음으로

**눈으로 본 뒤 새로 알게 된 불합격 조건은 되도록 `qa_sprite_check.py` 에 검사로
옮긴다** — 그래야 다음 바퀴가 같은 것을 눈으로 다시 찾지 않는다.

## 8. Godot 에 넣기

- PNG 는 `game/assets/sprites/` 에 저장한다.
- **저장 직후 반드시 재임포트한다** — 안 하면 옛 이미지가 그대로 로드된다:
  `/Applications/Godot.app/Contents/MacOS/Godot --headless --path game --import`
- 캐릭터는 `AnimatedSprite2D` + `SpriteFrames`(방향별 애니메이션)로 쓴다
  (`DESIGN.md` 「캐릭터 애니메이션」).
- **텍스처 필터는 nearest 여야 한다** — 이미 `project.godot` 에
  `default_texture_filter=0` 으로 잡혀 있다. 이게 풀리면 도트가 흐려진다.
- `*.png.import` 파일은 커밋한다 (`CLAUDE.md` 「git」).
- 화면 캡처는 `--headless` 로는 안 된다 — 다른 함정은 `docs/GOTCHAS.md` 를 볼 것.

## 9. 합격 기준

`DESIGN.md` 「그래픽 파이프라인」의 **"이질감이 없는가"**(어울림 + 자연스러움)를
그대로 따른다. 여기에 이 문서의 것을 더한다:

- [ ] **`qa_sprite_check.py` 가 통과하는가** — 아래 기계 판정 항목들은 여기서 끝난다.
      불합격이면 눈으로 볼 단계가 아니다
- [ ] **누가 봐도 "퀄리티 좋다"는 말이 나오는가** — 이게 멈추는 시점이다. 미달이면
      커밋하지 말고 미완료로 두고 `docs/STATUS.md` 에 어디가 부족한지 남긴다
- [ ] 배율이 정수인가 (아트 픽셀이 화면에서 균일한가)
- [ ] 팔레트 램프 밖의 색이 섞이지 않았는가 (검사가 봄)
- [ ] 외곽선이 순검정이 아닌가 (검사가 봄)
- [ ] 광원 방향이 기존 자산과 같은가
- [ ] 실루엣만 봤을 때 부위가 구분되는가 (내부선)
- [ ] 기존 자산 몇 개와 **실제로 나란히 놓고** 비교했는가

## 10. 참고 이미지

`docs/design_reference/` 에 둔다.

- `player_idle_x6.png` — 실제로 게임에 들어간 플레이어 idle 4방향을 6배로 키운 것
  (INBOX #8, 2026-09-06). **지금 자산의 기준선이다** — 새로 만드는 것은 이것과 같은
  팔레트·같은 도트 크기·같은 외곽선이어야 한다. 더 나은 결과가 나오면 갈아끼운다.
  원본은 `game/assets/sprites/player_idle.png`, 만든 코드는 `game/tools/gen_character.py`.
- 코어키퍼풍 참고 이미지는 사람이 로컬 `Draw Things.app` 으로 만들어 넣기로 했다.
  아직 없으므로 그때까진 위 기준만으로 판단한다.
- **AI 생성물을 게임 자산으로 쓰지 않는다** (`CLAUDE.md` 「그림 방식」 참고).
