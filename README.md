# 하네스 설계

`claude -p` 헤드리스 세션을 매 바퀴 새로 열어서, `docs/INBOX.md` 큐에 쌓인
작업을 한 바퀴에 하나씩 처리하는 자율 개발 루프다. 세션은 이전 바퀴의 대화를 기억하지
못한다 — 기억은 `docs/INBOX.md`/`docs/STATUS.md`/`docs/DESIGN.md` 파일이 대신한다.

## 한 바퀴의 흐름 (4단계)

## 루프는 둘이다 (2026-09-10)

기능과 그림은 **끝나는 방식이 달라서** 큐를 갈랐다. 기능은 「통과/불통과」인데
그림은 「후보 중 고르기」라, 같은 큐에 두면 도끼 날 하나로 열 바퀴를 도는 동안
기능이 멈춘다.

| | 명령 | 큐 | 규칙 | 보는 곳 |
|---|---|---|---|---|
| **기능** | `./ctl.sh start` | `docs/INBOX.md` | `docs/PROMPT.md` | [대시보드](https://kimtuna.github.io/Gunfarm/) |
| **그림·모션** | `./ctl.sh design start` | `docs/DESIGN_QUEUE.md` | [`docs/DESIGN_LOOP.md`](docs/DESIGN_LOOP.md) | [갤러리](https://kimtuna.github.io/Gunfarm/design.html) |

**그림 루프는 한 바퀴에 세션을 두 번 부른다** — 만드는 쪽(`docs/PROMPT_DESIGN.md`)이 후보를
굽고, 보는 쪽(`docs/PROMPT_CRITIC.md`)이 그 그림을 실제로 보고 **「무엇을 어떻게 재라」**를
내놓는다. 감상은 금지다: 이 프로젝트에서 진짜 문제를 잡아낸 것은 전부 측정이었고
눈으로 "괜찮아 보인다"고 한 판단은 전부 틀렸다(근거는 `DESIGN_LOOP.md`).

아래는 **기능 루프**의 흐름이다.

1. **읽기**: `docs/INBOX.md`는 전체를 읽지 않고 grep 등으로 번호가 가장
   작은 미완료 항목 하나만 찾아서 그것만 읽는다(완료된 옛 항목이 쌓여도 매 바퀴
   비용이 늘지 않게). `docs/STATUS.md` 전체, `docs/DESIGN.md` 전체. `[DESIGN]`
   태그일 때만 `docs/STYLE_GUIDE.md`도 전체 읽는다.
   (`docs/GOTCHAS.md`/`docs/VISION.md`는 매 바퀴 읽지 않는다 — 아래 참고.)
2. **개발**: 그 항목 하나만 만든다.
3. **자체 QA**: 실제로 실행해서 확인한다. 통과 못 하면 커밋하지 않는다.
4. **커밋 + push**: 세션이 직접 커밋하고 push까지 끝낸다.

세부 규칙은 `docs/PROMPT.md`에 있다 — 매 바퀴 세션에게 그대로 전달되는 지시서다.

## 설계 결정과 이유

- **하네스 지시서는 한 파일(`docs/PROMPT.md`)로 둔다.** 작업 종류(로직/그림)별로 파일을
  나누면 매 바퀴 읽어야 할 문서량과 유지보수 부담이 커진다 — 태그(`[BUILD]`/
  `[DESIGN]`)별 차이는 한 파일 안에서 짧게 분기하는 것으로 충분하다.
- **`docs/STATUS.md`는 매 바퀴 완전히 덮어쓴다.** 이전 내용을 "지난 바퀴 기록" 같은
  다른 이름으로 옮겨서 보존하지 않는다 — 그런 습관이 한 번 붙으면 파일이 무한정
  불어나서, 매 바퀴 그 문서 전체를 읽어야 하는 비용이 계속 커진다. 이력은 어차피 git
  커밋 메시지에 그대로 남으니 중복 보존할 필요가 없다. 재사용 가치가 있는 교훈은
  STATUS.md에 쌓아두지 말고 제자리로 옮긴다 — 재사용 가능한 검증 방법/스크립트는
  `game/qa/`에 코드로, 게임 설계 결정은 `DESIGN.md`에, 하네스 프로세스 규칙은 사람이
  검토한 뒤 `docs/PROMPT.md`에.
- **작업 커밋의 push는 세션이 직접 한다.** 4단계 흐름을 세션이 스스로 끝까지 수행하는
  게 가장 단순한 모델이다 — push를 별도 스크립트에 미루면 그 자체로 불필요한 개념적
  레이어가 하나 늘어난다. `loop.sh`는 진행 상황 대시보드 파일만 별도로 커밋+push한다.
- **`[ASK]` 태그가 붙은 항목은 세션을 열지 않고 바로 멈춘다.** 사람이 답을 줘야 하는
  물음은 세션을 몇 번 열어도 같은 결론이 나온다 — 답을 아는 주체가 세션이 아니기
  때문이다. 실제로 2026-09-07 에 그런 항목 하나가 보통 항목으로 들어와 세 바퀴를 돌며
  매번 "사람이 정해줘야 한다"에 도달하고 $19 를 태웠다. 아래의 연속 실패 감지가
  결국 잡긴 하지만, **그때는 이미 세 바퀴를 쓴 뒤이고 멈춤 사유도 "3회 연속 미완료"라는
  엉뚱한 것이 된다.** 태그로 미리 갈라내면 비용이 0 이고 사유도 정확해진다.
- **같은 INBOX 항목이 연속으로 실패하면(`STUCK_REPEAT_LIMIT`, 기본 3회) 루프를 멈추고
  알린다.** 예산/시간 초과 등으로 같은 항목이 계속 미완료로 남으면, 그 항목만 반복
  재시도하며 진전 없이 리소스만 소모할 위험이 있다 — 크레딧 부족 감지와 같은 방식으로
  다루고, 사람이 알아채고 개입할 수 있게 일찍 멈춘다.
- **`ctl.sh start`는 launchd로 실제 프로세스가 떴는지 몇 초 안에 확인하고, 확인이 안
  되면 직접 백그라운드 실행으로 폴백한다.** launchd의 수동 kickstart 호출은 실행
  환경에 따라 조용히 실패할 수 있다 — "시작됨"이라는 응답만 믿고 넘어가면 실제로는
  아무것도 안 도는 상태를 못 알아챌 위험이 있으므로, 시작 직후 반드시 확인한다.
- **대시보드는 최소한으로 유지한다.** 남은/완료 개수, 다음 항목, 마지막 커밋, 경고
  배너 정도면 진행 상황을 확인하는 데 충분하다.
- **`docs/GOTCHAS.md`(엔진/헤드리스 실행 자체의 기술적 함정 모음)는 STATUS.md와 반대로
  계속 쌓이는 파일이다.** 게임 설계도 아니고 특정 검증 스크립트 하나만의 문제도
  아닌, "엔진이 이렇게 동작한다"는 재사용 가치 있는 사실이라 STATUS.md처럼 매 바퀴
  버릴 수는 없다. **하지만 매 바퀴 필수로 읽지는 않는다** — 대부분의 바퀴는 이런
  엔진 문제를 아예 안 만나는데, 쌓여가는 파일을 매번 통째로 읽으면 STATUS.md가
  불어났을 때와 똑같이 바퀴마다 비용/시간이 계속 늘어난다. 대신 "실행 결과가
  예상과 다르거나 에러가 나면, 원인을 스스로 조사하기 전에 먼저 이 파일부터
  검색한다"는 **조건부 참조**로 바꿨다 — 실제로 문제를 만난 바퀴만 비용을 치른다.
  쓰기 쪽은 STATUS.md가 불어났던 것과 같은 문제를 피하려고 세 가지를 못박았다
  (자세한 형식은 `docs/PROMPT.md` 참고): 추가 전 중복 확인, "사실+대응법" 형식 고정
  (서술형 금지), 일정 줄 수를 넘으면 자동 추가 대신 사람에게 정리를 제안한다.
  **`loop.sh`를 실제로 만들 때는 이 줄 수 확인을 크레딧 부족 감지와 같은 방식으로
  스크립트가 직접 하게 만드는 것도 검토할 것** — LLM의 자율적인 판단에만 기대지
  않고 기계적으로 감지하는 편이 더 안전하다.
- **그림은 전부 이 기계 안에서 만든다 — 외부 API를 쓰지 않는다.** 외부 API에
  의존하면 잔액/크레딧 관리라는 부가적인 복잡도와, 실패했을 때의 재시도·대기
  로직까지 필요해진다 — 로컬 생성이면 이 복잡도 자체가 없어진다.
  **이 이유는 그대로지만 수단은 2026-09-08 에 바뀌었다.** 그전에는 파이썬 Pillow가
  수식으로 도트를 찍었고, 지금은 로컬 ComfyUI(SDXL + 픽셀아트 LoRA + ControlNet)가
  그림을 그린다. 둘 다 무료이고 이 기계 밖으로 나가지 않는다. 아래 「캐릭터 그림이
  만들어지는 흐름」 참고.
- **`DESIGN.md`에서 지금 당장 부딪힐 일이 없는 내용은 분리해뒀다.** `DESIGN.md`는
  "이번 바퀴와 무관해 보여도 전체를 다 읽는다"는 원칙이 있다 — 시스템끼리 서로
  얽혀 있어서(예: 아이템 크기 표준은 건축이든 요리든 다 적용됨) 일부만 골라 읽는
  건 위험하기 때문이다. 하지만 예외적으로 **절대 안 겹치는** 두 부분만 별도 파일로
  뺐다: `docs/VISION.md`(얼리억세스 이후 로드맵 — 지금 범위가 아니라고 문서 자체가
  명시함, 매 바퀴 읽지 않음), `docs/STYLE_GUIDE.md`(캐릭터 그림체 기준 — `[BUILD]`는
  정의상 그림을 안 만드니 이 태그일 때만 읽으면 됨, 이미 있는 태그 구분이라 새로운
  판단 위험이 없음). 이 두 경우가 아니면 함부로 DESIGN.md를 쪼개지 말 것.

## 캐릭터 그림이 만들어지는 흐름

**AI는 자세 하나만 그리고, 움직임은 프로그램이 만든다.** 이 한 줄이 이 파이프라인의
전부다 — AI에게 모션 프레임을 직접 뽑게 하면 프레임마다 캐릭터가 조금씩 달라져서,
걷기가 아니라 깜빡임이 된다(실측으로 확인했다).

1. **뼈대를 그린다** — 4방향(정면/옆/뒤/옆)을 2×2 한 캔버스에 넣는다.
   자세·비율·방향은 프롬프트가 아니라 **이 뼈대가 정한다.**
   `game/tools/comfy.py`
2. **ComfyUI에 주문한다** — 뼈대를 ControlNet(OpenPose)에 물려 넘긴다.
   GUI가 아니라 워크플로 JSON을 `POST /prompt` 로 보내므로 세션이 직접 주문할 수 있다.
   방향을 따로 뽑으면 같은 캐릭터가 안 나와서 **한 장에 네 자세를 받는다.**
3. **부품 10개로 자른다** — 머리 · 몸통 · 위팔/아래팔 ×2 · 허벅지/정강이 ×2.
   뼈대를 우리가 만들었으므로 **관절 좌표를 이미 안다.**
   `game/tools/rig.py`
4. **관절 각도로 조립한다** — 걷기도 도끼질도 각도표 한 줄이다.
   도구가 늘면 `rig.TOOLS` 에 이름 하나만 늘리면 시트 3장이 따라 나온다.
5. **맨 마지막에 줄인다** — 1024px에서 자르고 돌린 뒤 96px로 축소하며 색을 줄인다.
   도트는 이 한 번에서만 만들어지므로 중간 회전이 도트를 뭉개지 않는다.
   `game/tools/gen_player.py`

절차 전체와 「되돌리지 말 것」 목록은 `docs/CHARACTER.md` 에 있다.

### 루프는 이 흐름을 이렇게 돈다

- 항목이 `[DESIGN]` 이면 세션이 `docs/CHARACTER.md` 를 먼저 읽는다
  (`docs/PROMPT.md` 의 「캐릭터 그림을 건드릴 때」).
- 시트를 구운 뒤 **기계가 판정한다** — `game/qa/qa_character_sheets.py` 가
  규격·알파·발밑·머리 흔들림·프레임 이어짐·방향 간 색맞음을 재고 종료 코드로 답한다.
  게임 안 확인은 `game/qa/qa_player_world.gd` 가 창을 띄워 캡처까지 한다.
- **둘 다 종료 코드 0이 아니면 커밋하지 않는다.** 4단계 흐름의 3번(자체 QA)이
  그림 작업에도 똑같이 적용된다 — 사람이 눈으로 보는 것은 검사를 통과한 뒤다.

실제로 이 구조를 갖춘 뒤 루프에게 캐릭터 한 벌을 통째로 맡겼더니, 4방향을 한 장으로
뽑아 22개 시트를 굽고 검사를 통과시킨 뒤 스스로 커밋했다(INBOX #56).

## 실제 스크립트

`loop.sh`/`ctl.sh`/`env.sh` 는 위 설계대로 만들어져 있고 실제로 돌고 있다
(2026-09-08 기준 INBOX 55항목을 처리했다 — 이 절은 그전까지 "아직 만들지 않았다"로 남아
있었다). 이 문서는 **그 스크립트들이 지켜야 할 설계**이고, 스크립트를 고칠 때 여기
적힌 이유와 어긋나지 않는지 먼저 본다. 엔진 관련 알려진 함정은 `docs/GOTCHAS.md`에 있다.
